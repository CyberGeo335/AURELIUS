# Умный кредитный кабинет предпринимателя

Техническое задание, функциональные требования, Use Case и модели As Is / To Be.

Источник: [ABOUT.md](ABOUT.md).

## Статус документа

Документ структурирует исходный кейс и дополняет его предложениями для согласованного MVP. Это основа для дальнейшего уточнения, а не утвержденное техническое задание.

Статусы положений:

- **Из задания** — прямо указано в ABOUT.md.
- **Проектное предложение** — конкретизация для MVP, которую можно изменить.
- **Гипотеза** — предположение, требующее подтверждения исследованием.

Внешние источники не использовались. Описание As Is не является подтвержденной схемой внутренних процессов Альфа-Банка.

## 1. Техническое задание — ТЗ

### 1.1. Наименование

«Умный кредитный кабинет предпринимателя» — прототип цифрового кредитного конвейера для малого и микробизнеса.

### 1.2. Основание разработки

Кейс, изложенный в ABOUT.md. Необходимо объединить клиентский путь и внутреннюю обработку кредитной заявки в один работающий процесс.

### 1.3. Цель

Создать веб-продукт, в котором представитель бизнеса сможет выбрать кредитный продукт, подать заявку и получить результат, а банковская сторона — обработать заявку с использованием проверок, оценки риска и правил принятия решения.

Система должна сохранять данные и контекст между этапами, показывать актуальное состояние заявки и объяснять пользователю дальнейшие действия.

### 1.4. Задачи разработки

1. Исследовать потребности предпринимателей и банковской стороны.
2. Определить границы процесса, роли, этапы, данные и результаты.
3. Реализовать клиентский веб-кабинет.
4. Реализовать внутреннюю обработку заявок.
5. Разработать объяснимую модель скоринга и кредитного решения.
6. Объединить компоненты в сквозной сценарий с сохранением данных.
7. Подготовить автономный запуск и комплект материалов для проверки.

### 1.5. Пользователи и участники

| Участник | Назначение | Статус |
|---|---|---|
| Представитель малого или микробизнеса | Выбор продукта, оформление заявки, предоставление сведений, получение результата | Из задания |
| Сотрудник банка | Анализ нестандартных ситуаций, уточнение сведений, участие в решении | Участие описано в задании; конкретные полномочия определяет команда |
| Сервисы проверок | Предоставление сведений о компании и кредитной истории | Для проверяемой версии воспроизводятся локально |
| Автоматический обработчик | Проверки, расчет риска, применение правил, изменение состояния заявки | Проектное предложение по реализации |

Собственник, директор, бухгалтер и другие уполномоченные сотрудники — варианты представителя бизнеса. ABOUT.md не требует отдельных системных ролей для каждой должности.

### 1.6. Границы MVP

Предлагается включить:

- выбор кредитного продукта и параметров финансирования;
- заполнение и сохранение заявки;
- проверку полноты и корректности данных;
- запрос дополнительных сведений внутри продукта;
- обогащение данных через локальные симуляторы;
- расчет оценки риска;
- принятие решения по отдельным кредитным правилам;
- отображение результата и дальнейших действий;
- обработку случая, требующего участия сотрудника банка.

Подписание документов и выдачу средств допускается смоделировать. Их реализация — расширение основного сценария до получения результата по заявке.

**Предлагаемые исключения из MVP:**

- реальные банковские операции;
- реальные интеграции с корпоративными системами;
- обслуживание кредита после выдачи;
- взыскание задолженности;
- полноценная промышленная система управления кредитным риском.

Исключения необходимо явно зафиксировать в документации.

### 1.7. Основные данные

| Сущность | Содержание |
|---|---|
| Представитель | Идентификатор, сведения о пользователе, связь с компанией |
| Компания или ИП | Регистрационные сведения, статус бизнеса, вид деятельности |
| Кредитный продукт | Название, назначение, допустимые параметры, правила рассмотрения |
| Заявка | Компания, продукт, сумма, срок, цель, статус |
| Финансовые сведения | Доходы, расходы, обязательства и другие выбранные факторы риска |
| Результат проверки | Источник, результат, время выполнения, обнаруженные обстоятельства |
| Скоринговая оценка | Итоговая оценка риска и факторы, повлиявшие на нее |
| Кредитное решение | Результат, основания, предложенные условия |
| Запрос уточнений | Недостающие сведения, текст запроса, ответ клиента |
| История обработки | События и переходы между состояниями |

Это предлагаемая логическая модель. Точный набор полей зависит от выбранных продуктов и правил MVP.

### 1.8. Технические требования и ограничения

| Область | Требование из задания |
|---|---|
| Интерфейс | Клиентская часть имеет веб-интерфейс; мобильное приложение не допускается |
| Развертывание | Решение должно быть cloud-native и запускаться в Docker |
| Воспроизводимость | Все необходимые компоненты запускаются единым воспроизводимым способом на обычном ПК |
| Зависимости | Версии языка и ключевых библиотек зафиксированы |
| Данные | Используются синтетические сведения о клиентах, компаниях, сотрудниках, документах, заявках и финансах |
| Интеграции | Корпоративные системы Альфа-Банка не требуются; внешние проверки воспроизводятся локальными моками, стабами или симуляторами |
| Стоимость | Проверяемая версия не зависит от платных подписок, API, покупных данных и закрытых корпоративных лицензий |
| Каналы взаимодействия | Основной сценарий проходит внутри продукта, без обязательных писем, звонков, SMS и мессенджеров |
| Кредитная логика | Допускается упрощенная, явно описанная модель |
| LLM | При использовании разрешены только модели с открытыми весами |
| Облачная демонстрация | Желательна, но не обязательна |

Производительность, число одновременных пользователей, SLA, поддерживаемые браузеры и конкретные характеристики ПК в ABOUT.md не заданы.

**Дополнительные проектные требования:** разграничение доступа, защита от повторной отправки заявки, контроль допустимых переходов статуса, сохранение истории решений и понятная обработка ошибок.

### 1.9. Результаты поставки

Необходимо предоставить:

1. GitHub-репозиторий с историей коммитов.
2. Commit hash, тег или другой однозначный идентификатор версии на момент дедлайна. Более поздние коммиты не учитываются.

8. THIRD_PARTY_NOTICES со сторонними компонентами, моделями, датасетами, сервисами и указанием смоделированных интеграций.

10. Описание API, OpenAPI/Swagger и коллекцию запросов.
11. Диаграмму состояний заявки.
12. Модель данных.
13. Тестовые сценарии.

### 1.10. Предлагаемые критерии приемки

- Эксперт запускает решение по README на чистом окружении с необходимыми средствами запуска.
- Пользователь проходит путь от выбора продукта до результата рассмотрения.
- Сохраненные данные доступны после повторного открытия заявки; перезапуск компонентов не теряет подтвержденные записи.
- Статус соответствует фактическому этапу обработки.
- Неполная или некорректная заявка вызывает понятную реакцию системы.
- Запрос уточнений и ответ выполняются внутри продукта.
- Синтетические наборы позволяют воспроизвести одобрение, отказ и предложение иных условий.
- В интерфейсе и документации различаются оценка риска и кредитное решение.
- Основной сценарий работает без платных сервисов и корпоративного доступа.

## 3. Use Case — сценарии использования

### UC-01. Выбрать кредитный продукт

- **Основной участник:** представитель бизнеса.
- **Цель:** выбрать финансирование под потребность компании.
- **Предусловие:** доступны продукты с описанием назначения и условий.
- **Триггер:** у бизнеса возникла потребность в финансировании.

**Основной поток:**

1. Пользователь открывает раздел финансирования.
2. Изучает доступные продукты.
3. Выбирает продукт.
4. Указывает сумму, срок и цель.
5. Система проверяет соответствие параметров ограничениям продукта.
6. Пользователь переходит к оформлению заявки.

**Альтернатива:** параметры не подходят — система объясняет ограничение и предлагает изменить ввод. Автоматическая рекомендация другого продукта является дополнительной функцией.

**Результат:** выбран продукт и определены исходные параметры заявки.

**Связанные ФТ:** ФТ-01–ФТ-03.

### UC-02. Подготовить и отправить заявку

- **Основной участник:** представитель бизнеса.
- **Цель:** передать банку запрос на финансирование.
- **Предусловие:** выбран кредитный продукт.
- **Триггер:** пользователь начинает оформление.

**Основной поток:**

1. Система открывает форму заявки.
2. Пользователь указывает сведения о представителе и компании.
3. Вводит необходимые финансовые данные.
4. Система сохраняет введенные сведения.
5. Пользователь проверяет содержание и отправляет заявку.
6. Система выполняет итоговую валидацию.
7. Регистрирует заявку и запускает обработку.
8. Показывает идентификатор, статус и дальнейшие действия.

**Альтернативы:**

- Есть ошибки — система показывает их и сохраняет введенные данные.
- Пользователь прерывает заполнение — при реализации черновика может вернуться позднее.
- Повторная отправка той же заявки — предлагается возвращать результат первой операции без создания дубликата.

**Результат:** заявка зарегистрирована и передана в обработку.

**Связанные ФТ:** ФТ-03–ФТ-09, ФТ-16–ФТ-17, ФТ-21.

### UC-03. Предоставить дополнительные сведения

- **Основной участник:** представитель бизнеса.
- **Другие участники:** сотрудник банка или автоматический обработчик.
- **Цель:** устранить нехватку информации.
- **Предусловие:** при рассмотрении обнаружены недостающие сведения.

**Основной поток:**

1. Система или сотрудник формирует запрос уточнений.
2. Заявка переходит в состояние ожидания сведений.
3. Клиент видит запрос в кабинете.
4. Дополняет данные.
5. Система проверяет ответ и сохраняет его.
6. Обработка возобновляется с повторением зависимых проверок.

**Альтернативы:**

- Ответ неполный — система указывает, что еще требуется.
- Клиент не ответил — заявка остается в ожидании. Срок и правила закрытия такой заявки требуют отдельного решения.

**Результат:** сведения дополнены либо заявка остается в контролируемом ожидании.

**Связанные ФТ:** ФТ-07, ФТ-09, ФТ-12, ФТ-16–ФТ-17, ФТ-20.

### UC-04. Автоматически обработать заявку

- **Инициирующее событие:** отправка заявки или получение уточнений.
- **Участники:** автоматический обработчик, симуляторы источников данных.
- **Цель:** подготовить обоснованный результат рассмотрения.
- **Предусловие:** заявка содержит данные для запуска проверок.

**Основной поток:**

1. Система проверяет полноту и согласованность сведений.
2. Запрашивает данные локальных симуляторов.
3. Сохраняет результаты проверок.
4. Рассчитывает оценку риска.
5. Применяет кредитные правила с учетом продукта, суммы, срока и результатов проверок.
6. Формирует решение либо направляет заявку на ручное рассмотрение.
7. Обновляет статус.

**Альтернативы:**

- Недостаточно информации — запускается UC-03.
- Требуется экспертный анализ — запускается UC-05.
- Проверка недоступна — применяется выбранная политика повторной обработки; техническую ошибку не следует автоматически считать кредитным отказом.

**Результат:** сформировано решение либо определен следующий этап.

**Связанные ФТ:** ФТ-09–ФТ-15, ФТ-20, ФТ-26.

### UC-05. Рассмотреть нестандартную заявку

*Проектное предложение для реализации банковской стороны.*

- **Основной участник:** сотрудник банка.
- **Цель:** обработать случай, не завершенный автоматически.
- **Предусловие:** заявка направлена на ручное рассмотрение.

**Основной поток:**

1. Сотрудник открывает очередь.
2. Выбирает заявку.
3. Изучает данные, проверки, оценку риска и причину передачи.
4. При необходимости запрашивает уточнение.
5. Принимает решение в пределах заданных полномочий.
6. Указывает основание.
7. Система сохраняет решение и показывает клиенту результат.

**Альтернатива:** действие противоречит обязательному правилу — система блокирует его либо применяет явно предусмотренный механизм исключения.

**Результат:** решение зафиксировано или запрошены дополнительные сведения.

**Связанные ФТ:** ФТ-12, ФТ-14–ФТ-15, ФТ-19, ФТ-22–ФТ-24.

### UC-06. Получить результат рассмотрения

- **Основной участник:** представитель бизнеса.
- **Цель:** узнать результат и понять дальнейшие действия.
- **Предусловие:** рассмотрение завершено либо сформировано предложение условий.

**Основной поток:**

1. Пользователь открывает заявку.
2. Система показывает результат.
3. При одобрении отображает условия финансирования.
4. При предложении иных условий показывает измененные параметры.
5. При отказе показывает понятное сообщение.
6. Объясняет доступные дальнейшие действия.

**Расширение MVP:** клиент принимает или отклоняет предложение. При принятии система запускает моделирование оформления и выдачи.

**Результат:** клиент ознакомлен с решением; при реализации расширения зафиксирован его выбор.

**Связанные ФТ:** ФТ-15–ФТ-18, ФТ-25, ФТ-27.

## 4. As Is — текущее состояние

ABOUT.md содержит обобщенное описание кредитования. Поэтому ниже представлена **рабочая модель предметной области**, а не подтвержденная схема процессов Альфа-Банка.

### 4.1. Обобщенный текущий процесс

1. У бизнеса возникает потребность в финансировании.
2. Представитель определяет подходящий продукт и параметры.
3. Собирает сведения о компании и финансовом положении.
4. Передает заявку банку.
5. Банк проверяет полноту и корректность.
6. При необходимости уточняет данные.
7. Получает сведения из внутренних и внешних источников.
8. Оценивает риск.
9. Принимает решение с учетом дополнительных факторов.
10. Сообщает результат.
11. При положительном решении оформляет документы и предоставляет финансирование.

### 4.2. Проблемы и степень подтверждения

| Наблюдение | Что известно |
|---|---|
| Пользователю может не хватать банковской экспертизы | Прямо указано в задании |
| Потребности клиентов и параметры заявок различаются | Прямо указано |
| В обработке участвуют разные роли, системы и источники | Прямо указано |
| Часть операций требует участия сотрудника | Прямо указано |
| Сведения могут требовать дополнения | Прямо указано |
| Между этапами теряется контекст | Риск, на устранение которого направлен продукт; фактическая частота неизвестна |
| Клиенты повторно вводят одни сведения | Гипотеза о текущей проблеме; сокращение повторного ввода обозначено как цель |
| Клиентам непонятны статусы и следующие действия | Продуктовая проблема, которую следует проверить исследованием |
| Уточнения выполняются через звонки, почту или SMS | В ABOUT.md текущие каналы не описаны |

### 4.3. Что нужно выяснить для подтвержденной As Is

- Как клиент выбирает продукт сегодня?
- Какие сведения уже есть у банка?
- Где и почему возникает повторный ввод?
- Кто выполняет каждую проверку?
- Какие события вызывают ручное рассмотрение?
- Как запрашиваются уточнения?
- Какие статусы видит клиент?
- Сколько времени занимают этапы и где возникают задержки?
- Какие основания и полномочия используются при принятии решения?

Без этих сведений нельзя достоверно заявить, насколько новый продукт сократит сроки, затраты или число ошибок.

## 5. To Be — целевое состояние

### 5.1. Целевой процесс

1. Клиент открывает веб-кабинет.
2. Выбирает продукт с понятным описанием.
3. Задает параметры финансирования.
4. Заполняет заявку; система сохраняет сведения.
5. Получает подсказки об ошибках до отправки.
6. Отправляет заявку.
7. Система регистрирует ее и запускает обработку.
8. Выполняет проверки и получает синтетические сведения из локальных источников.
9. При нехватке информации запрашивает уточнение внутри кабинета.
10. Рассчитывает оценку риска.
11. Отдельно применяет кредитные правила.
12. При необходимости передает заявку сотруднику.
13. Формирует результат: одобрение, отказ или предложение иных условий.
14. Показывает клиенту результат и дальнейшие действия.
15. При реализации расширенного сценария фиксирует согласие и моделирует оформление и выдачу.

### 5.2. Предлагаемая модель состояний

| Состояние | Значение | Возможный следующий шаг |
|---|---|---|
| Черновик | Клиент заполняет заявку | Отправка |
| Подана | Заявка зарегистрирована | Проверка |
| Проверка данных | Выполняются проверки и обогащение | Уточнение, оценка риска |
| Требуются сведения | Ожидается ответ клиента | Возврат к проверкам |
| Оценка риска | Рассчитывается скоринговая оценка | Принятие решения |
| Принятие решения | Применяются кредитные правила | Решение или ручное рассмотрение |
| Ручное рассмотрение | Требуется действие сотрудника | Уточнение или решение |
| Одобрена | Финансирование одобрено на указанных условиях | Ознакомление или принятие предложения |
| Предложены иные условия | Сформировано альтернативное предложение | Принятие или отклонение |
| Отказ | Получено отрицательное решение | Завершение |
| Оформление | Моделируется подготовка и подписание | Моделирование выдачи |
| Выдана — симуляция | Смоделировано предоставление средств | Завершение |

Черновик, принятие предложения, оформление и симуляция выдачи — предлагаемые состояния. Технические ошибки лучше хранить отдельно от кредитного результата: например, как признак приостановки обработки с причиной.

### 5.3. Изменения относительно рабочей As Is

| Аспект | As Is: описание или гипотеза | To Be: целевое поведение |
|---|---|---|
| Выбор продукта | Клиенту может не хватать экспертизы | Понятные описания и ограничения |
| Данные | Используются на нескольких этапах | Сведения сохраняются в контексте заявки |
| Проверки | Распределены между источниками и участниками | Результаты связаны с единым процессом |
| Уточнения | Текущий механизм неизвестен | Запрос и ответ внутри продукта |
| Статус | Прозрачность требует исследования | Актуальный статус и следующие действия |
| Оценка риска | Один из элементов рассмотрения | Отдельный расчет с сохранением результата |
| Решение | Учитывает риск и другие факторы | Явные правила с учетом продукта и заявки |
| Работа сотрудника | Нужна в нестандартных случаях | Управляемая передача контекста на рассмотрение |
| Проверка прототипа | Реальные источники недоступны | Автономные симуляторы и синтетические данные |

### 5.4. Метрики для проверки эффекта

Числовые цели в ABOUT.md отсутствуют. Для исследования и оценки прототипа можно использовать:

- долю успешно завершенных заявок;
- время заполнения;
- число ошибок и повторных вводов;
- долю заявок, требующих уточнений;
- долю автоматического и ручного рассмотрения;
- время прохождения каждого этапа;
- долю пользователей, правильно понимающих статус и следующий шаг.

Целевые значения следует установить после исследования и определения границ MVP.
