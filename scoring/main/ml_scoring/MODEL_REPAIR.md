# Исправление экономической семантики скоринга

## Проблемы исходного подключения

1. `debt_to_revenue` из генератора — latent `base_debt`, а не наблюдаемый
   остаток долга / месячная выручка. В генераторе существующий месячный платёж
   равен `base_revenue * base_debt * 0.16`.
2. Генератор ограничивает DSCR диапазоном [.05,8], резерв [0,18] и др.; адаптер
   ранее подавал DSCR=18/27/41 напрямую и использовал другой долговой признак.
3. Исходный CatBoost не имел ограничений монотонности. В контролируемом профиле
   улучшение DSCR с 3.6 до 8 повышало PD12 примерно с 17.7% до 36.4%.
4. Всем предлагалась фиксированная ставка «публичный минимум + 2 п.п.».
   Если годовая экономика не проходила, индивидуальная цена не подбиралась.

## Новый контракт

`db_proxy_v2`, `db_auto_v3`, `db_diagnostic_v2`:

```text
model_base_debt_proxy = existing_monthly_debt_service / (0.16 * historical_mean_revenue)
model_dscr = clip(max(0, monthly_revenue * operating_margin) / existing_debt_service, .05, 8)
```

Первая формула — приближённая инверсия генератора: latent base_revenue неизвестна,
используется историческое среднее. Она не объявляется нормативным банковским
долг/выручка. Настоящий `outstanding_debt_to_monthly_revenue`, raw DSCR и все
ограничения диапазонов сохраняются отдельно в `financial_observations` и
`feature_adjustments`. Платёжеспособность считается по исходным деньгам и платежам,
не по ограниченным признакам модели. Коэффициент 0.16 имеет смысл только для
данной синтетической модели; его нельзя переносить на другое обучение без проверки.

## Модель

Новый кандидат обучается на CPU с ограничениями CatBoost:

- DSCR, cash_buffer, operating_margin, revenue_trend: риск не растёт при улучшении.
- Debt coefficient, overdue flag, amount, annual rate, macro stress, volatility:
  риск не снижается при ухудшении.
- `max_ctr_complexity=1`: сложные CTR-комбинации не обходят числовые ограничения.

Документация: https://catboost.ai/docs/en/references/training-parameters/common#monotone_constraints
GPU не поддерживает эти ограничения. Исходный модельный артефакт сохраняется
в `models/experiments/survival_v3_optuna_stage2`; прежний SHA/конфигурация —
`model/previous_model_info.json`.

Из-за RAM используется фиксированная случайная выборка до 35000 эпизодов только
из исходного train, seed=20261024. Validation используется целиком. Данные 30
компаний и доля одобрений не участвуют в обучении, выборе итерации или модели.
Критерий приёмки: validation weighted IPCW Brier не хуже исходной модели более
чем на 0.003, max decile calibration error <=0.06, ноль проверенных нарушений
монотонности. Протокол с фактическими метриками находится рядом с моделью.

Holdout сравнивает обе модели одной функцией `sksurv.metrics.brier_score`.
Это может отличаться от старого notebook-отчёта с собственной обработкой IPCW
на совпадающих дискретных временах. Сравнивать следует числа одного протокола.
Исходный test уже изучался при предыдущей оценке; это не новый внешний holdout.
Качество на синтетике не доказывает калибровку на реальных заёмщиках.

Фактическое сравнение текущих артефактов (меньший Brier лучше):

| Метрика | Исходная модель | dt_monotone_v1 |
|---|---:|---:|
| Validation weighted IPCW Brier | 0.125641 | 0.127814 |
| Test weighted IPCW Brier, один и тот же evaluator | 0.128336 | 0.130318 |
| Test max decile calibration abs error | 0.037464 | 0.029719 |

Brier немного ухудшился, семантические ограничения выполнены, максимальная
ошибка калибровки по децилям в этом протоколе уменьшилась. Нельзя интерпретировать
это как однозначное улучшение всех характеристик модели.

## Ограниченная черновая цена

В автоматическом/диагностическом MVP, если банк ещё не зафиксировал индивидуальную
ставку, диапазон: от публичного минимума +2 п.п. до 30% с шагом 0.5 п.п.
Потолок 30% — явное допущение проекта, не подтверждённый тариф Альфа-Банка.
Ограничение максимальной ставки каталога имеет приоритет. Сначала ищется
максимальная сумма, затем минимальная ставка, проходящая риск и платёжеспособность.
При изменении ставки заново рассчитываются платёж, PD и PD_limit, потому что
annual_rate входит в признаки. За пределы диапазона модельной генерации не выходим.
Переданная индивидуальная ставка без pricing_policy остаётся фиксированной.

Это не снижение LGD/расходов/маржи ради одобрений: экономическая политика БД
остаётся прежней. Результат — MANUAL_REVIEW и черновик; сотрудник подтверждает цену.

В отчёте requested_pd_12m соответствует исходной базовой цене, а pd_12m и
pd_limit_12m — найденным условиям. Для исходного запроса предусмотрены отдельные
requested_base_rate_pct и requested_base_pd_limit_12m. Не сравнивайте PD от одной
ставки с порогом от другой.

## Воспроизведение

Из корня проекта, с исследовательскими зависимостями из корневого requirements:

```cmd
python -m main.ml_scoring.train_monotone
python -m main.ml_scoring.validate_monotone_release
python -m main.ml_scoring.promote_monotone
python -m unittest discover -s main/tests -v
python -m main.batch --diagnostic --as-of 2026-10-24
```

Полные исследовательские артефакты находятся в `models/experiments/survival_v4_monotone`.
Скрипт promotion отказывается устанавливать не прошедший приёмку кандидат.
Изменения этого исправления не записывают ничего в рабочую БД.
