# AURELIUS: скоринг → решение → кредитное предложение

Пакет для передачи backend-команде. Для готового снимка данных:
`evaluate_application(snapshot, policy, predictor=None)`.
Он возвращает `Assessment`; `result.to_dict()` пригоден для JSON.
Для PostgreSQL достаточно `run_application(application_id, save=False)`:
данные и серверные MVP-настройки модуль получает самостоятельно. Расширенный
вызов с `context` и `policy` сохранён для явных внешних входов и тестов.

```python
from main.database import run_application

result = run_application(application_id=123, save=True)
```

DATABASE_URL задаётся в окружении процесса один раз. По номеру заявки читаются
компания, продукт, финансовые таблицы, история платежей, политика и ключевая ставка.
При недостаточных данных возвращается MANUAL_REVIEW с кодом DB_INPUTS_UNAVAILABLE;
фиктивные финансовые наблюдения не добавляются. DRAFT и CANCELLED заявки не оцениваются.

Политика подготовки входов `decision_engine/application_defaults.json` явно задаёт:
маппинг ОКВЭД, нейтральный синтетический macro_stress=0, предпочтительный график,
и **индикативный** диапазон ставки MVP: от базовой публичной + 2 п.п. до 30%,
с шагом 0.5 п.п. Потолок 30% — допущение проекта, не тариф банка. Если есть внешний
черновик предложения, используются его выбранные ставка/график. Это не
индивидуальная котировка банка; сотрудник должен её подтвердить.
Автоматический режим считает PD и условия при достаточных исходных данных,
но возвращает REVIEW_REQUIRED из-за неподтверждённых границ источников и proxy.
Эти допущения полностью входят в audit.snapshot, а не скрываются от backend.

Финансовому адаптеру нужны 13 полных положительных месяцев REVENUE в RUB,
верифицированная отчётность и известные обязательства/платежи с историей просрочек.
Если старые seed-сценарии не содержат таких сведений, результатом будет ручная
проверка. Пустота БД не заменяется подтверждением отсутствия долгов.

## Быстрый запуск

Из корня `scoring` (на Windows можно использовать `venv\Scripts\python.exe`):

```powershell
python -m pip install -r main/requirements.txt
python -m main.pipeline --snapshot main/examples/application.json --policy main/decision_engine/policy.demo.json
python -m unittest discover -s main/tests -v
```

Пример целиком синтетический. Ставка кредита 28%, ключевая ставка 15%, LGD 45%,
DSCR 1.20, нулевая стоимость капитала и прочие числа — **демо-допущения**,
не актуальные условия банка или ЦБ. `demo_only=true` сохраняется в результате.
Этот флаг обозначает происхождение расчёта; смена флага не калибрует модель.

Для передачи скопируйте **весь `main`**, включая `ml_scoring/model/best_model.cbm`,
в корень Python-проекта тиммейта. Для этой модели добавлено точечное исключение
из `*.cbm` в `.gitignore`; проверьте её наличие в архиве/коммите.
SHA256 записан в `ml_scoring/model/README.md`. Для Git коммитьте исходники `main`
и эту модель; локальные отчёты `main/reports` исключены из Git. Архив не требуется.
Исследовательские ноутбуки и большой датасет для инференса не нужны.

## Вызов из Python

```python
import json
from main import evaluate_application
from main.decision_engine.policy import Policy
from main.ml_scoring.predictor import Predictor

policy = Policy.load("main/decision_engine/policy.demo.json")
predictor = Predictor()  # создать один раз на процесс
with open("main/examples/application.json", encoding="utf-8") as file:
    result = evaluate_application(json.load(file), policy, predictor)
response = result.to_dict()
```

Результат содержит `decision` (`REJECT`, `MANUAL_REVIEW`),
`automatic_recommendation` (`POSITIVE`, `NEGATIVE`, `REVIEW_REQUIRED`),
`eligibility_status`, `reasons`, `offer`, `scoring`, `risk_assessment`, `audit`.
Успешная автоматическая проверка возвращает `MANUAL_REVIEW` + `POSITIVE`
и рассчитанный черновик предложения. При уменьшении суммы причина — `REDUCED_AMOUNT`.
`MANUAL_REVIEW` + `REVIEW_REQUIRED` означает нерешённый вопрос проверки;
это не положительная рекомендация. `APPROVE` устанавливает другой backend-обработчик
только после подтверждения авторизованным сотрудником банка. Пакет сам `APPROVE`
не возвращает и выдачи денег не делает.

`risk_assessment` содержит `pd_application_1y`, `pd_application_term`,
`pd_limit_1y`, `pd_limit_1y_raw`, горизонт сравнения, проверяемую сумму и результат
`passes_pd_limit`. PD передаются в долях: 0.08 означает 8%. До запуска модели
значения PD равны null; отказ по обязательному условию может не требовать скоринга.

`ConfigurationError` означает отсутствие/неоднозначность внутренней политики.
`InputError` означает некорректный или неполный вход предыдущего сервиса.
Этапы 4–6 не создают вопросы LLM и не возвращают `REQUEST_DATA` клиенту.
Интеграционный backend должен обработать эти ошибки отдельно от кредитного отказа.

## Контракт входа

Полный образец: `examples/application.json`. Backend, а не браузер, формирует
snapshot после аутентификации владельца, проверки комплектности и подтверждения.
Сервис проверки анкеты должен передать завершённую заявку (`COMPLETE`,
`SUBMITTED`/`UNDER_REVIEW`, `submission_confirmed=true`).

Из БД читаются `application`, `company`, `product`, применимая версия `terms`,
конкретные `rate_option` и `repayment_option`, `product_details`, правила допуска,
цели, комиссии, экономическая политика и ключевая ставка. Несколько действующих
политик или неоднозначный источник последней ставки — ошибка конфигурации.
Отсутствие записи о цели не превращается автоматически в запрет.

В расширенном режиме с явно переданным context от внутреннего backend/адаптера данных нужны:

- `as_of`: дата оценки, без использования будущих наблюдений.
- Индивидуальная `individual_annual_rate_pct` и её `individual_rate_source`.
  Публичная ставка «от» не выбирается автоматически.
- `model_features`, `feature_contract_version`, `feature_provenance` для каждого
  переданного признака. `requested_amount`, `annual_rate`, `entity_type` и возраст
  при наличии даты регистрации формируются пакетом.
- `capacity`: месячный денежный поток, доступный для обслуживания долга,
  действующий месячный платёж и `source`. Не берите платёж нового кредита из
  `requested_monthly_payment`: его пакет рассчитывает самостоятельно.
- `internal_confirmations`: результаты внутренних проверок юридических событий,
  кредитной истории, цели, комиссий и применимости поручительства.
  Это подтверждение проверки backend-командой, не пользовательское согласие.
- При пустых таблицах экономики — явные `risk_policy`, `economics_source`,
  `key_rate_pct`, `key_rate_source`, `key_rate_effective_date`.
  При наличии строк БД они имеют приоритет над fallback-контекстом.

В дампе v2 таблицы макроиндикаторов, экономической политики, дополнительных
критериев и комиссий пусты. Пакет не заполняет их выдуманными банковскими данными.

Для начального заполнения экономической политики добавлен `python -m main.seed_policy`:
по умолчанию dry run, `--apply` сохраняет значения. Источники, числа и границы
допущений описаны в `decision_engine/BASELINE.md`; фактическая ключевая ставка
отделена от внутренних допущений MVP. Уже заполненная БД используется без
передачи economic-параметров в context. После изменения рабочей БД требуется
новый полный версионированный дамп согласно `bd/README_versions.md`.

### Соответствие признаков обучению

| Признак | Единица / смысл |
|---|---|
| `age_months` | Полные календарные месяцы от регистрации |
| `industry` | retail/services/manufacturing/construction/transport/agriculture |
| `entity_type` | БД LEGAL_ENTITY → OOO; INDIVIDUAL_ENTREPRENEUR → IP |
| `monthly_revenue` | Выручка месяца на момент заявки, рубли |
| `revenue_trend_12m` | revenue(t)/revenue(t−12)−1 |
| `revenue_volatility` | Population std последних 12 месячных выручек / их mean |
| `operating_margin` | Operating cash flow / monthly revenue в генераторе |
| `cash_buffer_months` | Cash balance / monthly revenue, не / расходы |
| `dscr` | Operating cash available / обслуживание существующего долга |
| `debt_to_revenue` | Proxy base_debt = existing monthly debt service / (0.16 × historical mean revenue), ограниченный [.03,3]; наблюдаемый долг/выручка хранится отдельно |
| `prior_overdue_30d` | Бинарный признак; отсутствие строк без проверки полноты истории не означает 0 |
| `requested_amount` | Проверяемая сумма предложения, рубли |
| `annual_rate` | Доля единицы: 28% → 0.28 |
| `macro_stress` | Шкала генератора, может быть отрицательной; не ключевая ставка |
| `month_on_book` | Месяц прогноза 1..T, создаётся predictor |

**Граница точного соответствия обучению:** в исходном обучении `base_debt` генерируется
латентно, `macro_stress` — синтетическая календарная функция, `industry` не имеет
утверждённого маппинга ОКВЭД, а operating cash flow не равен автоматически
операционной прибыли отчётности. Поэтому пакет требует готовый проверенный
снимок этих признаков. Автоматического SQL-преобразования всех финансовых таблиц
в эквивалент обучающего вектора здесь нет. Формальное вычисление debt/revenue
и подстановка KEY_RATE создавали бы другой контракт модели.

Для работающего SQL-прототипа можно явно выбрать `feature_contract_version="db_proxy_v2"`
и `internal_confirmations.financial_history_complete=true`. Тогда адаптер читает
транзакции, отчётность, обязательства и историю платежей на дату оценки. Нужны
13 полных положительных месяцев рублёвых поступлений REVENUE, однозначная последняя
подтверждённая отчётность и положительные известные платежи по действующему долгу.
Выручка берётся за последний завершённый месяц, trend и volatility — по истории.
Операционная прибыль используется как явно обозначенный proxy денежного потока,
а синтетический base_debt восстанавливается приближённой инверсией формулы
генератора. Наблюдаемый долг/выручка хранится отдельно. DSCR и другие входы
ограничиваются так же, как в генераторе; сырые значения сохраняются в аудите.
Платёжеспособность может быть получена из тех же источников либо передана отдельно.
`industry` и `macro_stress` по-прежнему задаются явно с provenance.
Этот режим разрешён только с `demo_only=true`, все подстановки записываются в аудит.
Старый db_proxy_v1 оставлен только для воспроизведения прошлых сравнений.
Подробное описание исправлений модели и подготовки признаков — `ml_scoring/MODEL_REPAIR.md`.
Пустая история не подменяется нулями. В тестовых seed-сценариях есть только 12
месяцев операций; для такого случая передайте проверенные признаки или расширьте
тестовую историю отдельно, не выдавая её за реальные наблюдения.

## Как принимается решение

1. Проверить идентичность компании, продукта и версий условий; применимость
   продукта, сроки, нижнюю границу суммы, статус компании и внутренние проверки.
   Известное банкротство блокирует, текущая просрочка передаётся на ручную проверку.
2. Рассчитать свободный платёж:
   `cash_available / minimum_dscr − existing_debt_service`.
3. Перебрать суммы вниз от `min(запрошенная, максимум продукта)` с шагом политики.
   Если разрешена черновая риск-цена, для каждой суммы проверить ставки вверх
   в разрешённом диапазоне; вернуть наибольшую сумму по минимальной проходящей ставке.
   Явно заданная backend'ом индивидуальная ставка без pricing_policy не меняется.
   Дополнительно проверяются сама верхняя сумма и нижняя граница продукта.
   Возвращается **максимум на проверенной сетке**, не аналитический максимум
   до копейки. Перебор сохранён для совместимости с другими моделями и правилами;
   текущая модель имеет ограничения монотонности по сумме и другим факторам.
4. Для подходящей по платежу пары сумма/ставка повторно вызвать модель.
   Финансовые признаки момента заявки остаются фиксированными.
5. Проверить явно заданные ограничения PD, если они есть в `pd_limits`.
   Демо-политика не вводит произвольный PD-порог: словарь пуст.
6. Применить выбранный метод. В демо-политике `decision_method=annual_pd_limit`:
   рассчитать годовой лимит и сравнить его с PD12. Если все проверки пройдены,
   вернуть положительную рекомендацию сотруднику банка, а не окончательный APPROVE.

### Годовой лимит PD — основной метод MVP

```text
F = KEY_RATE + funding_spread
headroom_pct = individual_rate_pct − F − operating_cost_pct − required_margin_pct
PD_limit_1y_raw = (headroom_pct / 100) / (lgd_pct / 100)
PD_limit_1y = max(0, min(1, PD_limit_1y_raw))
passes = headroom_pct > 0 AND model_PD12 <= PD_limit_1y
```

Текущая версия БД AURELIUS_MVP_20261024_V1: KEY_RATE=14%, спред=1.5 п.п.,
расходы=2 п.п., требуемая маржа=3 п.п., LGD=45%. Фондирование=15.5%.
При ставке 29%: `(29−15.5−2−3)/45 = 0.188889`, то есть лимит PD12 ≈18.89%.
При 25.5% лимит ≈11.11%; при 30% — ≈21.11%. Сравнивается PD12, не PD36/PD60.
В `examples/application.json` намеренно другой, полностью автономный синтетический
набор параметров: он не отражает актуальные записи рабочей БД.
При LGD=0 годовой метод возвращает ConfigurationError; отрицательный запас
доходности не разрешает выдачу. Исходный лимит сохраняется до ограничения 0..1.
Формула является упрощённой экономической границей, а не нормативом банка.
Она не описывает детально амортизацию, повторные выборки и стоимость капитала.
Если эти издержки должны учитываться в данном методе, их нужно явно включить
в согласованные расходы/требуемую маржу, не считать, что они учтены автоматически.

### Дополнительная помесячная диагностика

`decision_method=monthly_cashflow` сохраняет альтернативную проверку по
неотрицательному дисконтированному вкладу. При годовом методе эти значения
также возвращаются как диагностика, но не являются дополнительным условием отказа.

Используется `PD(t)=1−product(1−hazard(m))`. В экономике за месяц:

```text
default_probability = survival_start * hazard
expected_interest  = survival_end * scheduled_interest
expected_loss      = default_probability * opening_principal * LGD
cost               = survival_start * opening_principal * annual_cost / 12
contribution       = expected_interest − expected_loss − cost
```

`annual_cost` включает KEY_RATE, funding_spread, operating_cost, required_margin
и явную capital_cost. Все проценты переводятся в доли. Взносы в резерв погашения
не считаются доходом банка. При LGD=0 нет деления на ноль. Это модель экономики
MVP с постоянными ставками и LGD, без досрочного погашения и задержек взыскания.
Одногодичная формула PD_limit из документации не сравнивается с многолетней PD.

### Продукты

- R01: аннуитет или равный основной долг; платёжеспособность проверяется по
  максимальному платежу графика, деньги округляются до копеек.
- R02: срок договора отдельно от транша. Для проверки мощности погашения
  используется процент на полный лимит плюс месячный резерв `лимит / срок транша`.
  Экономика консервативно предполагает полностью выбранный лимит весь договор.
- R03: аналогичный стресс полного использования; при сроке транша в днях для
  резерва берутся полные 31-дневные периоды, минимум один. Это явная консервативная
  условность, не банковский график овердрафта. Каталожное OTHER не заменяется
  аннуитетом. Реальный cash sweep и поведение выборок требуют отдельного адаптера.

Подписки/дополнительные услуги и непустой каталог комиссий направляются на
`MANUAL_REVIEW`: их стоимость и применимость не формализованы в исходной БД.

Модель проверялась для сроков 12/18/24/36/48/60 месяцев, на горизонтах строго
внутри договорного срока. Например, для T=36 оценены PD6/12/24. Полная PD36
вычисляется, но не выдаётся за отдельно подтверждённую метриками.
`allow_unvalidated_term_pd=true` в демо-политике явно разрешает использовать
горизонты вне проверенного набора в демонстрации. В годовом методе это касается
PD12 при T=12: в исходной оценке для такого срока проверялась только PD6.
Если false, такой случай идёт на ручную проверку без положительной рекомендации.
Для помесячного метода флаг относится к полной кривой.
При других сроках модель возвращает InputError, не округляет срок молча.

## PostgreSQL

```powershell
$env:DATABASE_URL = "postgresql+psycopg://USER:PASSWORD@127.0.0.1:5433/business_scoring"
python -m main.pipeline --application-id 123 --context main/examples/context.demo.json --policy main/decision_engine/policy.demo.json
# Автоматический режим без финансового context:
python -m main.pipeline --application-id 123
# Добавить --save только для записи результатов в выбранную БД.
```

В `context.demo.json` замените готовые синтетические признаки данными именно
оцениваемой компании. Пример не должен использоваться для массового расчёта
разных компаний с одним финансовым вектором.

Адаптер использует транзакцию REPEATABLE READ и блокировку строки заявки.
Скоринг, решение, предложение и неизменяемый DECISION-снимок записываются атомарно.
При сбое любого INSERT всё откатывается. Повтор с тем же снимком, политикой
и хешем модели возвращает прежние идентификаторы, не создавая дубликаты.
Повтор после изменения контекста создаёт новую ревизию аудита.

`scoring_results.pd` хранит PD на максимальном **оценённом** горизонте,
а `feature_snapshot` хранит сам горизонт, всю кривую и признаки проверенной суммы.
`risk_grade=UNRATED`: отдельные границы классов риска не выдумываются.
Срок в месяцах хранится в `application_product_terms` и аудите.
В автоматическом результате `credit_decisions.decision=MANUAL_REVIEW`,
`approved_amount` и `approved_term_days` остаются NULL. Рассчитанные условия
хранятся в `application_product_terms` со статусом `DRAFT`, а PD и допустимый
лимит — в снимке скоринга, условиях предложения и DECISION-аудите.
Backend сотрудника после подтверждения должен отдельно зафиксировать APPROVE
и утверждённые условия; не следует обновлять неизменяемый DECISION-снимок.
Месяцы не превращаются автоматически в 30-дневные интервалы.
Статус заявки адаптер не меняет: backend должен отдельно провести акцепт
предложения, особенно при уменьшении суммы.

Необходимо авторизовать владельца заявки **до** вызова `run_application`.
Пакет — внутренняя Python-библиотека, не самостоятельный сервис аутентификации.
Для параллельных обновлений профиля backend должен повторить оценку перед
финальным принятием предложения. Ошибки сериализации БД можно безопасно повторять.

## Проверки

### Оценка всех 30 тестовых компаний

Для сравнения финансового риска бизнесов **независимо от CANCELLED-заявок**:

```cmd
set "DATABASE_URL=postgresql+psycopg://postgres:YOUR_PASSWORD@127.0.0.1:5433/business_scoring"
python -m main.batch --diagnostic --as-of 2026-10-24 --product R01 --amount 3000000 --term 36
```

Создаётся только гипотетический запрос в памяти для каждой компании, одинаковые
продукт/сумма/срок для сравнения. Реальные заявки и БД не меняются. Отчёты:
`main/reports/diagnostic.csv` и `diagnostic.json`. POSSIBLE_OFFER означает, что
подобрана финансово допустимая сумма (возможно меньше запрошенной), REJECT — что
нет подходящей суммы, UNSCORABLE — отсутствует необходимый признак.
Это условный финансовый результат при допущении завершения анкеты и проверок,
не фактическое одобрение банковской заявки.

Диагностический контракт при 6–12 последовательных наблюдаемых завершённых
месяцах приближённо оценивает 12-месячный тренд годовым лог-линейным наклоном,
volatility — по доступному окну. Наблюдения текущего незавершённого месяца исключены.
Эти подстановки записываются в источники признаков; финансовые операции не
дорисовываются. Для обычного API по-прежнему требуется полная история.
requested_pd_12m/term — PD при исходно запрошенной сумме и базовой цене;
requested_base_rate_pct и requested_base_pd_limit_12m относятся к той же цене.
pd_12m/term, pd_limit_12m и annual_rate_pct относятся к найденным условиям предложения.
Нельзя сравнивать PD одной цены с лимитом другой. Даже отказы по платёжеспособности содержат
отдельную диагностическую PD исходного запроса, если все признаки доступны.
Доля одобрений на 30 намеренно подобранных синтетических сценариях — sanity check,
не измерение калибровки или качества на реальном портфеле.

Последний диагностический прогон 24.10.2026, R01, 3 млн ₽, 36 месяцев:
24 возможных предложения (23 на полную сумму, одно на 750 тыс. ₽),
4 отказа по платёжеспособности, 2 случая без скоринга из-за отсутствия ОКВЭД/даты
регистрации. Большинство обычных профилей проходят под 29–29.5%, а не 25.5%.
Эти результаты условны: короткая история и proxy явно обозначены; это не
фактические одобрения и не целевой процент одобрений для настройки модели.

Для проверки обычного рабочего пути только по отправленным заявкам:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://postgres:YOUR_PASSWORD@127.0.0.1:5433/business_scoring"
.\venv\Scripts\python.exe -m main.batch --as-of 2026-10-24
```

Отчёт: `main/reports/businesses.csv` (разделитель `;`, UTF-8 BOM) и `businesses.json`.
Список компаний берётся из `bd/seeds/aurelius_30_ids.csv`; продукт и действующая
заявка — из БД, не из устаревшего сценарного описания CSV. Для каждой компании
выбирается последняя SUBMITTED/UNDER_REVIEW заявка. NO_ACTIVE_APPLICATION означает,
что нужно начать новую заявку в личном кабинете. Отменённые заявки не используются.
Пакетный запуск никогда не создаёт заявки, не меняет статусы и не сохраняет решения.
EVALUATED означает, что вызов выполнен; PD может быть null при недостатке данных,
конкретная причина указана в reasons. Отчёты исключены из Git.

Unit-тесты используют детерминированные fixtures; отдельные семантические тесты
загружают настоящую модель. Обучение и Ollama для тестов не нужны.
Опциональные PostgreSQL-тесты требуют **отдельную пустую тестовую БД** с именем
`aurelius_test*`, актуальной схемой и четырьмя продуктовыми справочниками:

```powershell
$env:AURELIUS_TEST_DATABASE_URL = "postgresql+psycopg://USER:PASSWORD@127.0.0.1:55439/aurelius_test_scoring"
python -m unittest discover -s main/tests -v
```

Тесты проверяют одобрение/снижение/отказ, ставки и единицы признаков,
сохранение основной суммы графика, DSCR, транши R02/R03, немонотонный риск,
ошибки внутренних параметров, изоляцию, откат записи и повторяемость.
Полный последний прогон — 41 тест, включая PostgreSQL и реальные model-regressions.
