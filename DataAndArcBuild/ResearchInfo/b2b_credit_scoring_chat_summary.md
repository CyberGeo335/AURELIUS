# Кредитный скоринг B2B и ММБ: выжимка обсуждения

Дата выгрузки: 22 октября 2026 года.

Документ суммирует содержательную часть текущего чата: данные, таргеты, признаки, обучение, кредитное решение, эксплуатацию и практические примеры. Это тематический конспект, а не дословная стенограмма. Технические предложения из обсуждения отделены от краткого обзора исходной статьи. Все числовые примеры ниже синтетические.

## 1. Исходный материал и границы задачи

Источник: [Tensoria — Credit Risk Scoring with Machine Learning: A B2B Guide](https://tensoria.fr/en/blog/credit-risk-scoring-ml).

В статье рассматривается прогноз неплатежа B2B-контрагентов при торговом кредитовании, страховании и оценке поставщиков. Основные входы: счета и платежи, финансовая отчётность, юридические события, характеристики компаний и CRM. Предлагаются логистическая регрессия, градиентный бустинг, survival-подходы; обсуждаются SHAP, интеграция в ERP/CRM, ручной пересмотр и мониторинг. Автор приводит ориентировочные этапы: аудит 2–3 недели, разработка 4–6, интеграция 3–4. Упоминаются 2–3 года истории и десятки дефолтов. Это ориентиры автора, а не универсальные критерии достаточности данных или гарантии качества. Готовых таблиц данных и кода статья не предоставляет. Регуляторные утверждения статьи в этом конспекте не используются как актуальная юридическая инструкция.

Дальнейшая схема — техническое развитие обсуждения для банковского кредитования малого и микробизнеса. Она добавляет платёжную нагрузку, параметры сделки, калибровку PD, временную валидацию и механизм решений.

## 2. Бизнес-постановка и границы ответственности

**Задача:** оценить риск будущего дефолта предпринимателя и использовать эту оценку при выборе допустимых условий финансирования.

| Понятие | Определение | Важное различие |
|---|---|---|
| Credit risk scoring | Оценка вероятности неплатежа | Не равен вероятности покупки продукта |
| Application scoring | Оценка на дату новой заявки | История отношений с банком может отсутствовать |
| Behavioral scoring | Периодическая оценка действующего клиента | Доступна история обслуживания долга |
| Антифрод | Выявление мошенничества | Требует отдельной постановки и таргета |
| Cash-flow forecasting | Прогноз денежных поступлений и расходов | Может помогать оценке платёжеспособности |
| Кредитное решение | Применение политики с учётом риска, нагрузки и сделки | Одной PD недостаточно |

Скоринговая модель возвращает вероятность события. Кредитная политика и продуктовый калькулятор определяют допустимость суммы, срока и графика.

## 3. Четыре модуля системы

| Модуль | Функция | Вход | Выход |
|---|---|---|---|
| A. Данные и выборка | Проверка, объединение, разметка и расчёт признаков | Заявки, события, отчётность, платежи | Исторически корректная витрина |
| B. Модель риска | Обучение, валидация, калибровка, объяснения | Признаки на дату оценки | PD за заданный горизонт |
| C. Кредитное решение | Проверка продукта, нагрузки, структуры и экономики сделки | PD, сведения о клиенте, параметры продукта | Решение и условия |
| D. Эксплуатация | Журналирование, мониторинг, обратная связь | Расчёты и фактические исходы | Алерты и обновления системы |

**Полный путь:** потребность → заявка → сбор и проверка данных → состояние компании на дату оценки → признаки → PD → платёжеспособность → расчёт условий → решение → объяснение → наблюдение за исходом → обновление системы.

## 4. Постановка ML-задачи и таргет

| Параметр | Пример постановки |
|---|---|
| Объект | Компания-заёмщик на дату заявки |
| Момент прогноза | До принятия решения |
| Событие | Первый дефолт после даты оценки |
| Горизонт H | 12 месяцев |
| Положительный класс | Дефолт в интервале (t, t + H] |
| Отрицательный класс | Полный горизонт наблюдался, дефолта не было |
| Незрелое наблюдение | Горизонт ещё не завершился; автоматически нулём не размечается |

Формально: `y(i,t)=1`, если согласованное событие произошло в `(t,t+H]`; `y(i,t)=0`, если весь горизонт наблюдался без события.

### DPD и горизонт — разные величины

**DPD (Days Past Due)** — длительность просрочки обязательства. **Горизонт прогноза** — будущий период, в котором ищем событие.

Пример: «Вероятность первого достижения установленного критерия дефолта в течение следующих 12 месяцев». Критерий может учитывать существенную просрочку, списание и другие согласованные события; его нужно зафиксировать в политике разметки.

| Ситуация | Правило |
|---|---|
| Компания уже в дефолте | Отдельный процесс, исключение из модели первого дефолта |
| Горизонт не завершился | Не присваивать `y=0` автоматически |
| Подача иска | Не считать любой иск дефолтом |
| Техническая задержка учёта | Проверять экономический смысл события |
| Изменение графика | Использовать согласованные правила разметки |
| Заявка отклонена | Отказ не равен дефолту: исход по невыданному кредиту неизвестен |

## 5. Договор на данные

Для каждого поля сохраняем:

- название и экономический смысл;
- источник и право доступа;
- ключ компании, договора или обязательства;
- дату события и дату доступности информации;
- периодичность обновления;
- валюту и единицу измерения;
- проверки качества и обработку пропусков.

**Point-in-time корректность:** при историческом расчёте можно использовать только информацию, доступную к дате оценки. Отчётность за прошлый год нельзя использовать до фактического поступления или публикации.

### Почему нужна таблица распределения платежей

Один платёж может закрывать несколько счетов, а один счёт — оплачиваться частями. Прямое соединение «один платёж = один счёт» искажает задолженность и DPD.

### Проверки качества

| Проверка | Предотвращаемая ошибка |
|---|---|
| Дубликаты компаний, договоров и операций | Повторный учёт |
| Валюты и денежные единицы | Ошибки сумм и коэффициентов |
| Частичные оплаты, возвраты, отмены | Неверный остаток долга |
| Изменения договорного графика | Ложная просрочка |

## 7. Каталог признаков

Таблица ниже — проектный каталог для витрины, а не готовая спецификация источников. Доступность каждого признака проверяется отдельно.

| Семейство | Примеры | Правило расчёта / интерпретации |
|---|---|---|
| Обслуживание долга | Максимальная просрочка, доля просроченной суммы, число эпизодов | Разделять текущий уровень и историю |
| Погашения | Доля погашенной суммы, частота частичных оплат | Учитывать распределение платежей |
| Платёжная динамика | Изменение задержек по временным окнам | Проверять уровень и направление изменения |
| Обороты | Поступления и списания за 30/90/180/365 дней | Исключать переводы между собственными счетами |
| Устойчивость потоков | Волатильность, дни без поступлений, минимальные остатки | Учитывать сезонность |
| Концентрация | Доля крупнейшего и пяти крупнейших покупателей | Зависимость от отдельных контрагентов |
| Финансовое положение | Чистый долг, оборотный капитал, рентабельность, операционный поток | Контролировать экономическую применимость |
| Платёжная нагрузка | Существующие платежи, новый платёж, покрытие обслуживания долга | Согласовать определение доступного потока |
| Параметры заявки | Сумма к обороту, срок, цель, обеспечение | Описывают конкретную сделку |
| Качество данных | Возраст отчётности, длина истории, доля пропусков | Отсутствие данных не равно нулю |

### Как строить динамические признаки

Для показателя рассчитываем уровень, изменение и устойчивость изменения. Пример с поступлениями:

1. Сумма за последние 90 дней.
2. Сумма за предыдущие сопоставимые 90 дней.
3. Темп изменения.
4. Изменение к тому же сезону прошлого года.

У сезонного бизнеса последовательное квартальное падение может отражать сезонность, поэтому нужен сопоставимый исторический период.

Пример ключа: `company_id + scoring_date + application_id`. Для поведенческой витрины без заявки используется ключ компании и даты оценки.

| Блок | Содержание |
|---|---|
| Идентификаторы | Компания, заявка, дата |
| Признаки | Только известные к дате оценки |
| Качество | Свежесть и полнота |
| Горизонт | Дата окончания наблюдения |
| Таргет | Исход и статус зрелости |
| Воспроизводимость | Версия источников и расчётов |

Заполнение пропусков, кодирование, отбор признаков и другие обучаемые преобразования настраиваются только на train.

## 9. Обучение и временная проверка

### Последовательность

1. Сформировать ранний обучающий период.
2. Использовать следующий период для настройки.
3. Выделить независимые данные для калибровки.
4. Проверить итог на более позднем нетронутом тесте.
5. При каждом историческом запуске учитывать, какие таргеты уже были известны на тот момент.

`TimeSeriesSplit` иллюстрирует разделение по времени, но для кредитных данных дополнительно нужны правила зрелости таргетов, временных разрывов и повторных наблюдений компаний.

### Сравниваемые варианты из обсуждения

| Вариант | Роль |
|---|---|
| Текущая кредитная политика | Бизнес-база сравнения |
| Логистическая регрессия | Простой объяснимый baseline |
| CatBoost / LightGBM | Проверка ценности нелинейных взаимодействий |

Сравнение проводится на одинаковых популяции, периоде и условиях. Эта таблица отражает варианты, обсуждавшиеся в текущем чате; окончательный выбор архитектуры модели здесь не утверждался.

### Дисбаланс и калибровка

Взвешивание классов может улучшить отдельные показатели классификации и одновременно ухудшить вероятности. В документации LightGBM это отдельно отмечено для `is_unbalance` и `scale_pos_weight`.

Калибровка нужна, чтобы назначенная PD соответствовала частоте событий на сопоставимых наблюдениях. Калибратор обучается независимо от данных обучения основной модели. Его качество оценивается на данных с достаточным числом событий.

## 10. Метрики

| Уровень | Метрики / проверки | Что показывает |
|---|---|---|
| Ранжирование | ROC-AUC, Gini, KS, Average Precision | Отделение более рискованных компаний |
| Вероятности | Reliability diagram, predicted/observed default rate | Соответствие PD частоте событий |
| Вероятностная ошибка | Brier score, log loss | Качество вероятностного прогноза в целом |
| Бизнес-эффект | Потери при одинаковом одобрении | Снижение риска при сопоставимом объёме |
| Бизнес-эффект | Одобрение при одинаковом уровне риска | Потенциал роста выдач |
| Экономика | Доход после потерь и расходов | Полезность для бизнеса |
| Устойчивость | Результаты по времени, продуктам, отраслям, новым/действующим клиентам | Где модель работает хуже |

**Уточнения:** Brier score не изолирует только калибровку; при редких дефолтах показываем неопределённость метрик. Высокое качество на нескольких событиях не доказывает устойчивость.

После запуска доступность метрик различается: технические показатели видны сразу, полноценный дефолтный исход — после необходимого горизонта наблюдения.

## 11. Объяснения и выход скорингового сервиса

Минимальный результат:

```text
Компания / заявка / дата оценки
PD и горизонт
Версия модели и калибратора
Полнота и свежесть данных
Основные факторы прогноза
Причины решения кредитной политики
```

**Факторы модели и причины решения хранятся отдельно.** Риск может быть приемлемым, но продукт недоступен по условиям или не проходит проверка нагрузки.

SHAP объясняет выход выбранной модели, а не причинно-следственную связь. Шкала зависит от режима объяснения: raw-выход и вероятность имеют разные единицы. Вклады нельзя автоматически подписывать как процентные пункты PD. При отдельной калибровке также нужно понимать, объясняется ли исходная модель или весь итоговый прогноз.

## 12. Механизм кредитного решения

| Шаг | Проверяем |
|---|---|
| Доступность продукта | Сегмент, цель и условия |
| Достаточность информации | Можно ли принять обоснованное решение |
| Риск | PD и применимые риск-факторы |
| Платёжеспособность | Покрытие действующих и новых обязательств |
| Структура сделки | Сумма, срок, график, обеспечение |
| Экономика | Доход с учётом потерь и расходов |
| Действие | Одобрение, альтернативные условия, ручной разбор, запрос данных, отказ |

### PD, LGD, EAD

| Параметр | Значение |
|---|---|
| PD | Вероятность дефолта за заданный горизонт |
| LGD | Доля потерь при дефолте |
| EAD | Задолженность на момент дефолта |
| EL | Ожидаемые денежные потери в упрощённом расчёте |

Упрощение: `EL = PD × LGD × EAD` при согласованных горизонте и допущениях. Это не полная модель бухгалтерского ECL: для неё нужны соответствующая методология, сроки, сценарии и дисконтирование.

Для MVP LGD и EAD могут быть документированными сценарными допущениями. Их нельзя представлять как обученные прогнозы, если таких моделей нет.

## 13. Практический кейс: приемлемая PD, но нет запаса платежей

**Все значения синтетические.** Запрос: 3 млн ₽ на 24 месяца.

| Показатель | Значение |
|---|---:|
| PD на 12 месяцев | 4% |
| Сценарная LGD | 45% |
| Сценарная EAD | 3 000 000 ₽ |
| Упрощённые ожидаемые потери | 54 000 ₽ |
| Месячный поток для обслуживания долга | 260 000 ₽ |
| Действующие месячные платежи | 100 000 ₽ |
| Новый месячный платёж | 160 000 ₽ |

Расчёты:

```text
EL = 0,04 × 0,45 × 3 000 000 = 54 000 ₽
Покрытие = 260 000 / (100 000 + 160 000) = 1,0
```

Новый платёж здесь принят как условный результат продуктового калькулятора; ставка и полный график не заданы. Покрытие 1,0 означает отсутствие запаса в принятом сценарии. Приемлемая PD сама по себе не обосновывает одобрение исходных условий.

Возможные действия: пересчитать меньшую сумму, другой график либо направить заявку аналитику. Пороги и допустимые действия определяются кредитной политикой.

## 14. Другие полезные ситуации из обсуждения

| Ситуация | Ошибка, которую легко допустить | Правильный подход |
|---|---|---|
| Отчётность опубликована позже заявки | Использовать её в прошлом | Проверять дату доступности |
| Несколько счетов оплачены одним переводом | Неверно рассчитать просрочку | Распределять платёж по обязательствам |
| Новый клиент без истории | Считать отсутствие данных хорошим поведением | Отдельно учитывать длину истории и сегмент |
| Сезонное падение поступлений | Принять сезонность за ухудшение | Сравнивать с аналогичным сезоном |
| Отказанная заявка | Присвоить дефолтный таргет | Считать исход невыданного кредита неизвестным |
| Хороший AUC, неверная PD | Использовать вероятность для потерь без проверки | Проверять и калибровать вероятности |
| Высокая метрика на малом числе дефолтов | Объявить модель надёжной | Оценить неопределённость и устойчивость |
| Дрейф признаков | Автоматически переобучить модель | Сначала расследовать источник изменения |

## 15. Эксплуатация и воспроизводимость

На каждый расчёт сохраняются:

- заявка и дата;
- версия исходных данных и признаков;
- версия модели и калибратора;
- PD и объяснения;
- версия кредитной политики;
- решение и предложенные условия;
- ручное изменение с причиной;
- последующий фактический исход.

| Слой мониторинга | Показатели | Когда доступны |
|---|---|---|
| Технический | Ошибки источников, задержки, доступность | Сразу |
| Данные | Пропуски, свежесть, новые категории, распределения | По мере поступления |
| Решения | Одобрения, альтернативные предложения, ручные разборы | По мере решений |
| Риск | Дефолты и соответствие PD исходам | После накопления зрелых наблюдений |
| Экономика | Потери и доходность | По мере накопления результатов |

При ухудшении проверяем поломку источника, изменение сегмента, политики и внешних условий. Затем выбираем исправление данных, изменение маршрутизации, перекалибровку либо переобучение.

## 16. ИИ-ассистент в кредитном кабинете

Этот блок описывает интерфейс вокруг скоринга и не требует LLM внутри модели PD.

| Компонент | Ответственность |
|---|---|
| Ассистент | Понять потребность, запросить сведения, вызвать сервисы, объяснить результат |
| Извлечение документов | Структурировать поля с привязкой к документу и странице, проверить значения |
| Скоринговый сервис | Рассчитать PD по проверенным признакам |
| Калькулятор продукта | Рассчитать платежи и допустимые параметры |
| Decision engine | Применить утверждённую политику |
| Аналитик | Рассмотреть предусмотренные случаи и документировать изменения |
