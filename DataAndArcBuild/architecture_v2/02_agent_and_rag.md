# V2 · диалоговый агент и RAG

## Новый workflow

LangGraph содержит собственные узлы `route → execute → project`. Вход — доверенный actor, типизированная команда и загруженный V2-кейс. Выход — `View` с состоянием, диагностикой, доступными действиями и возможностями. Доменное сохранение выполняется вне графа одним repository transaction; старые checkpoints не используются.

### Диалог

1. Определить справочный вопрос. Явные изменяющие просьбы не направлять в RAG.
2. Для обычного сообщения вызвать структурированное извлечение, если оно настроено.
3. Независимо проверить поля через Pydantic и дословную цитату текущего текста. Неверное поле не уничтожает пригодных соседей; допускается одна repair-попытка.
4. Сохранить `Proposal` с ID, patch, clear_fields, цитатами и источником сообщения. Подтверждённый request на этом шаге не меняется.
5. Показать карточку «Да, верно / Поправить». Команда `CONFIRM_FACTS` применяет только актуальное предложение. Правка в форме — отдельный `UPDATE_REQUEST`, без LLM.
6. Записать изменения как CLIENT/UNVERIFIED, пересчитать кандидатов и вернуть один следующий вопрос по замечаниям/неизвестным обязательным полям.

Сведения компании, роль, согласия, ставки, PD и решения не извлекаются как полномочия. Чатовая просьба отменить обращение лишь предлагает отдельную кнопку `CANCEL`; текст модели сам по себе не совершает отмену. Несколько субъектов/потребностей требуют уточнения, а не выбора за клиента.

Для текущего модельного адаптера сохранён `gpt-oss:20b`, структурированная JSON-схема и temperature=0. Это не гарантия правильности LLM: обязательны валидация и отдельные eval/live-проверки. Валидация повторённых известных значений также проверяет их соответствие новой цитате.

## Почему RAG сохраняется

Вопросы о полях, обязательности, форматах и источниках полезны независимо от стадии кейса и доступности Ollama. Их нельзя решать выдумыванием требований моделью. Переиспользуется существующий read-only FAISS/LangGraph RAG через V2-адаптер `ReferenceKnowledge`.

- Источник — `knowledge/Требования к кредитным заявкам.json`, 99 требований R01–R03.
- Область — продукт и ИП/ООО; упоминание ООО в справочном вопросе не меняет legal_form клиента.
- Ответ — выдержки, field_code, source_ref/JSON Pointer и SHA-256 версии источника.
- Изменение источника создаёт новую версию индекса; старый receipt остаётся связан с прежним ответом.
- NOT_FOUND/UNAVAILABLE/UNSUPPORTED_LEGAL_FORM показываются явно. За пределами справочника нет придуманной policy.
- Источник не даёт согласие, не подтверждает компанию и не запускает бизнес-действия.

Оставлен локальный TF-IDF/FAISS без внешнего embedding API. Recall естественных формулировок ограничен текущим retrieval; точный код поля предпочтителен для адресной справки. Изменять общий индекс/источник V1 ради экспериментального V2 следует отдельным изменением с регрессией обеих версий.

## Доступность и восстановление

`extraction_configured` означает наличие адаптера, а не успешную проверку работающего Ollama. Отсутствие LLM не блокирует форму и RAG. History, pending, ошибки и request хранятся в V2-агрегате; браузер не является единственным владельцем диалога.

`DataResolutionPlan` разделяет ASK_USER и ENGINEERING. Отсутствие адаптера M3–M5 — задача интеграции; клиент не должен отвечать на вопрос «какая формула признака правильная». В 0.1 узкий DB lookup legal_form не подключён: `database_lookup=UNSUPPORTED`, поле уточняется у клиента. Будущий read-only lookup требует actor/company/cutoff и действующего согласия.
