# V2 · контракты состояния и доступа

## Идентичность

`Actor(actor_id, company_id, borrower_id, role, grants)` создаёт доверенная граница. HTTP-тело команды не содержит этих полей. Запрет смены компании действует независимо от текста чата и выбранного в браузере профиля. Проверяется вся тройка owner/company/borrower, а не один ID компании.

На этапе ядра локальный gateway привязывает один BORROWER-профиль из операторских CLI-аргументов к секретному токену окружения. Это инструмент разработки, не клиентская авторизация V2 и не операторский кабинет. Обычный пользователь не должен вводить ID компании вместо входа. При подключении WEB gateway заменяется/дополняется серверной сессией с реестром клиентов и разрешений.

## Команда

```json
{
  "request_id": "form-change-001",
  "action": "UPDATE_REQUEST",
  "case_id": "V2-...",
  "expected_version": 4,
  "arguments": {"patch": {"amount_rub": 1500000, "term_months": 12}}
}
```

Все действия существующего кейса адресованы явно. Нет изменяемой глобальной «текущей заявки», в которую может попасть сообщение другой вкладки. `CREATE` принимает version=0, без case_id и аргументов; ID создаётся сервером, устойчив к повтору исходной команды. V2 допускает несколько черновиков; ресурсы не определяются последним выбранным кейсом.

## Два счётчика

- `version` — версия агрегата для конкурентных команд. Растёт при каждом зафиксированном ходе, включая справочный ответ и диагностированную ошибку. GET не меняет version.
- `revision` — версия финансового запроса/продуктового контекста. Изменения параметров или выбранного маршрута инвалидируют производные результаты. Справочный вопрос её не меняет. Извлечение без подтверждения тоже не меняет.

Ход RAG обновляет history/receipt, но не request, pending, выбранный продукт, evidence или решение. Изменение формы отменяет устаревшее предложение извлечения. `CONFIRM_FACTS` проверяет и version, и proposal_id.

## Commit и повторы

PostgreSQL transaction берёт V2 advisory lock владельца, сверяет receipt и ожидаемую version. Кейс, receipt ответа и аудит фиксируются атомарно. Повтор исходного request_id с тем же содержимым возвращает сохранённый ответ до проверки старой expected_version. Другой payload с тем же ID даёт 409. Привязка владельца включена в hash.

После нового конфликтующего действия нужно перечитать кейс и сформировать новый ID. После неизвестного сетевого исхода повторяют исходную команду с прежним ID/payload. Клиентское отключение кнопки не заменяет эти гарантии.

V2 SQL создаёт только `aurelius_agent_v2.cases/receipts/audit`; bootstrap выполняется отдельной командой, не при каждом запросе. Схема не удаляет/импортирует V1 и не восстанавливает backup. Модель агрегата и SQL — новая версия 0.1; будущие изменения payload требуют версионных миграций, а не молчаливого изменения старых JSON.

## Бизнес-эффекты

M3–M5 реализуются через `BusinessModules`. У адаптера должны быть собственные квитанции, связь с case/revision/evidence и восстановление неизвестного исхода. Откат transaction кейса не отменяет совершённый внешним сервисом эффект. Поэтому произвольный HTTP-вызов без журнала операций нельзя выдавать за готовый адаптер. В поставке ядра такой адаптер отсутствует.

Ответ бизнес-порта проверяется на совпадение case/revision/company/borrower. Операторская проверка входов и кредитное решение не входят в разрешённые borrower-команды. Доступ OPERATOR к чужим кейсам потребуется описать отдельно; сам выбор такой роли не даёт права вызвать borrower API.
