# Граница данных

Все кредитные экраны используют `CreditApi` через провайдер `src/app/context.tsx`. Компоненты не читают и не изменяют кредитный localStorage напрямую. Сессия демо-входа хранится отдельно в sessionStorage; в двух вкладках можно открыть разные роли.

`MockCreditApi` — единственная реализация кредитного контура в MVP. Он сохраняет всё состояние под ключом `aurelius-v2-credit-v1`, публикует неизменяемые снимки для `useSyncExternalStore`, принимает `storage`-события между вкладками. Запись защищена Web Locks API там, где он доступен; fallback — синхронная запись localStorage. Перед каждой командой читается актуальный снимок. Это локальное демо, а не серверная авторизация или транзакционная БД.

## Карта будущей интеграции

HTTP-адреса модулей 3–5 пока не определены; ниже сопоставлены методы и данные, а не придуманные готовые эндпоинты.

| Методы / данные CreditApi                      | Будущий владелец и таблицы                                                                                                                                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `createDraft`, `saveDraft`, `submit`, `cancel` | Заявка: `credit_applications`, `application_details`, `application_product_details`, `application_field_values`. Модуль 1 сохраняет запрос, модуль 2 — продукт и требования.               |
| Конфигурация `fields.ts`                       | `application_field_requirements` + явный безопасный маппинг `target_db_field`. 99 требований из исходного CSV, отбор по R01–R03 и ИП/ООО. Строки DB field не исполняются как SQL.          |
| `getSnapshot`, профиль и досье                 | Модуль 3: `companies`, `company_contacts`, `company_bank_accounts`, `financial_statements`, `bank_transactions`, `company_data_provenance`, `data_quality_checks`.                         |
| `requests`, `answerRequest`                    | Модуль 3: `application_data_requests`, `application_field_values`, `application_field_history`; ответ закрывает дозапрос и создаёт новую ревизию.                                          |
| `revisions`, аудит и версии                    | `application_snapshots`, `application_field_history`, `company_data_provenance`. Каждое событие содержит revision, модель, политику и snapshot reference.                                  |
| `tick` и этапы                                 | Статус оркестратора модулей 1–5. В реальном адаптере — серверные события или polling, без клиентского принятия решения по таймеру.                                                         |
| Модель / PD / платёжеспособность               | Модуль 4: `scoring_results`, `credit_obligations`, `risk_policy_parameters`. Риск и покрытие — отдельные показатели. Значения риска из V2 синтетические; отсутствие оценки остаётся явным. |
| `bankDecision`, предложения                    | Модуль 5: `credit_decisions`, `application_product_terms`, `credit_product_terms`; обязательны текущая ревизия, уполномоченный сотрудник, основание и версия политики.                     |
| `revise`, `accept`                             | Новая ревизия отзываeт все предложения предыдущей. `application_product_terms.offer_status`: PROPOSED → ACCEPTED, с проверкой срока действия и текущей ревизии на сервере.                 |
| `sign`, `fund`                                 | В MVP только SIGNED_DEMO и FUNDED_DEMO. Для реальной подписи/выдачи нужен отдельный доверенный контур модуля 5.                                                                            |
| `reset`                                        | Только локальное демонстрационное действие. Не переносить в production API.                                                                                                                |

Таблица соответствия статусов UI, заявок, диалога и предложений находится в `src/domain/status.ts`. NEEDS_INFO, MANUAL_REVIEW и недоступность внешнего источника не трактуются как отказ.

## Существующий помощник

`HttpChatApi` обслуживает только подтверждённые пути существующего Python-сервера:

- `GET /api/health`;
- `GET /api/chat/state`;
- `POST /api/chat` с `{message_id, text}` и `credentials: include`.

Клиент повторяет 428 один раз с тем же `message_id`; 409, 503 и транспортная ошибка требуют явного повтора с прежним ID. 400 показывает ошибку сообщения. Прокси Vite меняет Host через `changeOrigin` и Origin на `http://127.0.0.1:5173`.

`VITE_API_MODE=mock` включает автономный кредитный кабинет и сообщает, что помощник не подключён. `VITE_API_MODE=http` добавляет существующий живой чат, сохраняя MockCreditApi для кредитных экранов: готовых HTTP-модулей 3–5 сейчас нет. Серверная личность помощника управляется существующим сервером и не совпадает автоматически с выбором демо-профиля в новом UI. Факты из ответа чата показываются как неподтверждённые сведения; кредитная форма и отдельные согласия остаются явными. API помощника не подменяется ответами мока.

Пользовательские файлы не отправляются ни в чат, ни в кредитный сервер: в демо сохраняются только имена. Анализ и безопасное хранение содержимого — будущая интеграция модуля 3.
