## Что показывает диалог

В чате есть один актуальный **общий лог модулей 1–2**; предыдущий лог заменяется, сообщения диалога сохраняются:

- case_id, revision, status, режим DEMO;
- субъект и форма бизнеса, цель, сумма, срок, дата потребности;
- известные обязательства, обеспечение, сезонность, источник возврата и повторяемость потребности;
- обязательные уточнения отдельно от всех неизвестных полей;
- этап, выполненные операции, чего ждём, следующий шаг и модуль;
- код диагностики, например `MODULE_NOT_CONFIGURED`;
- продукты-кандидаты, причины, статусы условий «подходит / не подходит / неизвестно», ограничения и документы;
- полный общий JSON результата и трассировка инструментов в отдельном раскрывающемся блоке.

Неизвестные значения остаются явно неизвестными. «Срочность / дата» — поле `needed_by` исходного модуля; самостоятельная оценка срочности не придумывается. Лог строится из сохранённого результата оркестратора, а не из свободного текста модели. Ответ пользователю формирует существующий workflow по структурированному статусу; LLM извлекает изменения и дословные подтверждения из текста.

Модуль 2 подключён через `ProductModuleAdapter` по умолчанию в web и CLI. После подбора ожидается `WAITING_DOCUMENTS`, `next_module=3`, `next_action=CONNECT_MODULE`, `error_code=MODULE_NOT_CONFIGURED`: модули 3–5 пока недоступны. Кандидаты и требования сохранены, сбор документов не запускался. Если маршрута нет, модуль возвращает запрос уточнений `CLARIFY_PRODUCT_NEED`, а не кредитный отказ.

Каталог — `personalCab/prom/prom_lab/ai_agents_lab/catalog/products.json`, все 16 направлений. Карточки проектные: неизвестные банковские пороги и актуальность дают `UNKNOWN`. Результат не является одобрением. Каталог, профильные факты и их актуальность входят в `context_hash`; изменение запроса создаёт новую ревизию, изменение правил/подтверждённых фактов пересматривает подбор в текущей ревизии. Подробный контракт: `DataAndArcBuild/architecture/02_product_matching.md`.

## Проверочный диалог

1. «Нужно три миллиона рублей на товар» → сумма 3 млн и цель `INVENTORY`; уточнение формы и срока.
2. «Я ИП, деньги нужны на 24 месяца» → тот же case_id, подбор и требования готовы, следующий модуль 3.
3. «Измени сумму на пять миллионов рублей» → новая ревизия того же кейса, сумма 5 млн.
4. «Закупки постоянные, каждый месяц» → приоритет ВКЛ.
5. «Теперь цель — покупка автомобиля» → автокредит и лизинг, новая ревизия.
6. Перезагрузить страницу → история и последний лог восстанавливаются из SQLite.

«Обновить» восстанавливает диалог и последний лог без вызова LLM, очистки заявки или создания новой сессии. История диалога ограничена последними 16 сообщениями согласно модулю 1; все результаты ходов сохраняются в его таблице аудита. Новый текст отправляется с новым message_id; при транспортной ошибке «Повторить запрос» использует прежний message_id. Ошибка извлечения, уже сохранённая модулем 1, не маскируется: повторный разбор требует нового сообщения.

## API

Сервер отдаёт frontend и API с одного origin:

- `GET /api/health` — наличие Ollama и модели (без генерации).
- `GET /api/chat/state` — история и последний результат текущего браузерного профиля; устанавливает HttpOnly cookie.
- `POST /api/chat` — `{ "message_id": "unique-id", "text": "сообщение" }`.

Подтверждённые факты и продуктовые правила не принимаются через HTTP-запрос клиента. Субъект (`BORROWER-DEMO-PETYA`), владелец, роль и разрешения задаются сервером. Cookie продолжает DEMO-профиль после перезапуска. При первой отправке без cookie сервер сначала создаёт сессию и возвращает 428 с инструкцией повтора. Пользовательский текст не выдаёт согласия и не меняет роль. Сервер слушает только `127.0.0.1`; это локальная DEMO-граница, без production-аутентификации.

Файлы из вложений остаются в браузере и не анализируются. Для модуля 1 можно вставить HTTP(S)-ссылку в текст: сервер передаёт её как непроверенную `document_ref`, не скачивая документ. Загрузка и анализ файлов потребуют отдельной интеграции.

## Остальной кабинет

Финансовые показатели и компания демонстрационные. Черновики раздела «Мои заявки» по-прежнему хранятся в localStorage и **не синхронизированы** с кейсом диалогового workflow. Банковские операции, решения, ставки и скоринг не реализованы.

- `index.html`, `styles.css`, `app.js` — кабинет и HTTP-клиент чата.
- `server.py` — локальный HTTP API и адаптер к модулю 1.
- `tests/test_chat_server.py` — интеграционные тесты API и SQLite.
- `landing.html`, `landing.css`, `landing.js` — сохранённая рекламная страница.
- `front_assets/` — локальные иконки и иллюстрация.
