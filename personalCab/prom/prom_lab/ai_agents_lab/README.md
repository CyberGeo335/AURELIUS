# AURELIUS — модуль 1: диалог и управление заявкой

Реализация [спецификации](../../../../DataAndArcBuild/architecture/01_dialogue_and_workflow.md) на LangChain/LangGraph. Паттерн исходного агента-брокера и декомпозиция — в [AURELIUS.md](AURELIUS.md).

Ядро: локальный **Ollama `gpt-oss:20b`**. Другие модели не используются. Runtime работает в `DEMO`.

## Реализовано

- Типизированный запрос, неизвестные поля, намерение и patch с дословными цитатами из текущего сообщения.
- LangGraph: `load_case → extract_intent → advance_workflow → respond → persist`.
- Structured output с обязательной nullable-схемой. Одна корректирующая попытка при неверной схеме или недословной цитате, затем явная ошибка без выдумывания сведений.
- Уточнение субъекта, формы, цели, суммы и срока. Дата потребности, источник возврата, сезонность, обязательства и обеспечение остаются неизвестными, пока клиент их не сообщит.
- Все состояния модуля 1, проверка переходов, запрет изменения завершённого кейса.
- SQLite: кейсы, привязки сессий, квитанции сообщений, аудит и checkpoints LangGraph.
- Повтор сообщения возвращает сохранённый результат; другой текст с тем же id вызывает конфликт. Кейс восстанавливается после перезапуска. Новая сессия текущего субъекта продолжает его активный кейс.
- Изменение запроса обновляет ревизию и сбрасывает зависимые результаты. Запрос клиента не подменяется одобренными условиями.
- Проверка роли, владельца, субъекта, стадии и согласия перед зависимым tool-call.
- Восемь LangChain tools с `content_and_artifact`: `load_case`, `find_existing_application`, `update_request`, `get_product_candidates`, `get_data_requirements`, `request_evidence`, `get_assessment_status`, `get_bank_status`.
- Стабильный ключ внешнего вызова: case + revision + operation. Ответ другого субъекта/кейса/ревизии отвергается.
- Ссылки на документы сохраняются без скачивания и без присвоения им статуса проверенного факта.

## Подключение модулей 2–5

По умолчанию работает `UnconfiguredModules`. Полный запрос получает `REQUEST_READY`, `next_module=2`, `error_code=MODULE_NOT_CONFIGURED`: это точка передачи модулю 2, а не подбор продуктов или одобрение.

Передайте в `WorkflowApp(..., adapter=...)` объект с методом `ModuleAdapter.call(operation, envelope, idempotency_key)`. Envelope содержит case_id, revision, mode, borrower_id, запрос, ссылки на результаты и документы. Адаптер возвращает `ModuleResult` с теми же case_id/revision/borrower_id, `result_ref` и данными. Изменяющая операция обязана обеспечить идемпотентность по ключу. Неподдерживаемая операция возвращает ошибку либо `ModuleUnavailable`.

Ссылки на существующие внешние `assessment`/`bank_application` находятся в `Case.result_refs`. Их записывает доверенный интеграционный контур с проверкой ревизии; LLM и CLI не назначают их из текста клиента. В этом этапе нет callback endpoint, отправки заявки кредитору, расчёта ставки, PD или графика платежей.

Tools выбирает граф, а не LLM. Ответ строится по структурированному статусу: сбой сервиса не становится кредитным отказом. `COMPLETED` возможен после подтверждённого результата адаптера заявки; в DEMO это не реальная выдача.

## Доверенный контекст

В приложении `ActorContext` формируется сервером после аутентификации. CLI — локальная демонстрационная граница: actor-id, роль, субъекты и файл согласий передаются вызывающей стороной. Это не production-аутентификация.

- `--borrower-id` выбирает субъект; `--allowed-borrower-id` задаёт разрешённые субъекты. Для другой компании нужна отдельная сессия.
- `--consents-file` читает доверенный JSON-массив с полями `consent_id`, `borrower_id`, `scope`, `granted_at`, `expires_at`; даты содержат timezone. Scope: `EVIDENCE_COLLECTION`, `CREDIT_ASSESSMENT`, `BANK_STATUS`.
- `--deny-scope` фиксирует отказ; просроченное согласие не разрешает вызов.
- Фраза «согласен» в чате не выдаёт согласия. Зависимый запрос без действующего согласия не выполняется.

Хранилище предназначено для локального DEMO на POSIX/macOS. Ходы одного владельца сериализуются файловой блокировкой. Записи проверяются по storage_version; кейс, квитанция сообщения и аудит фиксируются атомарно. После сбоя незавершённого хода повтор начинается от последнего зафиксированного кейса. Безопасность повтора внешнего эффекта требует идемпотентности адаптера; checkpoints не обеспечивают exactly-once для внешнего сервиса.

Проверенные факты сохраняются отдельно и не используются модулем 1 для финансовых выводов. Актуальность и область применимости перед использованием проверяет будущий модуль 3. Для нескольких целей выполняется уточнение; автоматического создания связанных дочерних заявок пока нет. Исходный агент в `lab/ai_agents_lab` сохранён отдельно.

## Проверки

```bash
/Users/retro0/projects/PyVenv/venv_core/bin/python -m pytest personalCab/prom/prom_lab/ai_agents_lab/tests -q
```

29 тестов используют явные fixtures вместо Ollama и банков: восстановление, повторы, ревизии, неизвестные данные, изоляция субъектов, согласия, ошибки tools, внешние статусы и подтверждение завершения. Отдельно проверены характерные ошибки локальной модели: недословная цитата, повтор уже известных полей и неверная метка отмены для изменения суммы.

Реальный `gpt-oss:20b` проверен отдельно: сообщение «Нужно три миллиона рублей на товар» даёт `NEEDS_INPUT`; после перезапуска уточнение формы ИП и срока 24 месяца даёт `REQUEST_READY` для того же case_id; повтор message_id возвращает идентичный ответ; изменение суммы на 5 млн ₽ создаёт следующую ревизию. Модуль 2 при этом остаётся явно неподключённым.
