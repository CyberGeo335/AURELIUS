# 10. План развития и проверка результатов

План опирается на `main` **a5d90c3** от 26.10.2026, включающий исправления c549a06 и Windows-запуск 68b7b57. Текущий результат — связанный процесс R01–R03: клиент готовит заявку, сотрудник рассматривает её и принимает решение, клиент принимает опубликованное предложение. Следующий шаг — проверить удобство этого процесса на пользователях и последовательно расширить работу с данными и продуктами.

Приоритеты ниже — предлагаемый порядок развития команды, а не календарные обязательства. Переход между этапами определяется проверенным результатом. Принятые решения сохраняются в [02](02-decisions.md); возможности текущей версии — в [11](11-strengths.md).

| Ассистент предлагает поля с цитатами; клиент подтверждает изменения | измерять качество извлечения и удобство совместной работы формы и диалога |
| Зарегистрированный CatBoost, экономическая политика и расчёт условий | оценивать применимость входов, качество риска и устойчивость политики раздельно |
| Версии, квитанции запросов, снимки расчётов и контроль актуальности предложения | сохранять воспроизводимость при расширении данных и числа пользователей |

Удобство, экономия времени и качество кредитного риска на реальных данных проверяются отдельными исследованиями.

## 2. Последовательность этапов

### Этап 1. Зафиксировать воспроизводимый демонстрационный контур — P0

**Результат для команды:** единая проверенная версия для показа жюри и пользовательских тестов.

Зафиксировать для демонстрации hash объединённой версии, версии модели и политики, дамп и сценарии; проверить обе роли, подачу R01–R03, сообщения об ошибках и повторы запросов на отдельной БД. Основной комплект документов и Windows-запуск сохранены при слиянии; инвентарь объединённого кода уже актуализирован в [08](08-testing.md). Перед следующим показом подтверждать выбранный набор сценариев на фактической версии стенда.

**Критерий готовности:** документированный запуск с чистого окружения, сохранённый результат согласованного набора проверок, отсутствие незавершённых блокирующих дефектов клиентского и банковского маршрутов. Тест повторной подачи не создаёт вторую операцию, клиентская проекция содержит только разрешённые поля и причины. Проверки Linux-контейнера и Windows launcher фиксируются отдельно.

Зависимости: доступная модель, отдельная тестовая БД, согласованный сценарий демонстрации. Основание: [развёртывание](09-deployment.md), [контракты API](06-api.md), [проверки](08-testing.md).

### Этап 2. Проверить удобство клиента и сотрудника — P1

**Результат для пользователя:** понятное оформление и рассмотрение заявки без потери контекста между экранами, формой и диалогом.

Провести интервью и наблюдаемые задания отдельно с представителями малого бизнеса/ИП и сотрудниками, знакомыми с кредитным процессом. Проверить поиск нужного действия, обязательные реквизиты, подтверждение ассистента, ответ на дозапрос и чтение условий. Сначала измерить базовый сценарий с формой, затем сравнить с доступным ассистентом на сопоставимых заданиях. Согласия и подтверждения проверять как осмысленные действия пользователя.

**Критерий готовности:** протоколы заданий и ошибок по обеим ролям, измеренная исходная воронка, список исправлений по влиянию на завершение задачи и повторная проверка изменённых экранов. Даты, состав участников и условия исследования сохраняются вместе с выводами. Численные критерии предлагаются в разделе 3 и утверждаются перед пилотом.

Зависимости: стабильный контур этапа 1, сценарии и участники. Улучшения интерфейса можно выпускать независимо от подключения новых источников данных.

### Этап 3. Расширить данные с контролем происхождения — P1

**Результат для банка:** сведения из профиля, ответа клиента, документа и внешнего источника можно различить, проверить и использовать в расчёте по понятному контракту.

| Направление | Что добавить к текущей реализации | Критерий готовности |
|---|---|---|
| Реестр, БКИ, выписка | сначала локальные симуляторы с версиями контрактов, затем адаптеры согласованных источников | фиксируются источник, дата доступности, результат запроса и причина отсутствия; сбой не подменяется пустым успешным ответом |
| Исправления профиля | отдельный процесс принятия сотрудником исправления реквизита; сейчас `verify` сохраняет проверку, но не меняет `companies` | права, согласование, журнал изменений и пересмотр зависимых расчётов проверены сценариями конфликтов и повторов |
| Извлечение из выписки | разбор согласованного формата, проверка валюты/периода/единиц, сверка итогов и привязка извлечённого значения к источнику | набор размеченных примеров и отрицательных случаев; неоднозначный документ требует проверки; результат не становится подтверждённым автоматически |
| Ассистент | расширить набор диалогов, неоднозначных ответов, попыток неверного изменения и сбоев модели | измеряются корректность поля, цитата, сохранение уже известных значений и доля предложений, требующих исправления |

Зависимости: согласованные контракты данных, доступ и основания обработки, версии схем и тестовые примеры. Файловое хранение и извлечение в признаки — отдельные шаги. Наличие RAG по требованиям не означает доступ к внешним реестрам.

### Этап 4. Подготовить управляемый пилот — P1, параллельно с этапом 3

**Результат для команды внедрения:** измеримая работа под согласованной нагрузкой и восстановление после сбоя.

- Ввести производственную аутентификацию, жизненный цикл учётных записей и паролей; согласовать права, сроки хранения и обработку данных.
- Настроить HTTPS и доверенный публичный Origin. Реализованный резерв UUID для HTTP решает совместимость генерации ID; защищённый внешний доступ требует отдельной настройки.
- Добавить наблюдаемость с идентификатором операции, метрики задержек/ошибок API и LLM, контроль доступности БД без записи секретов и пользовательских сообщений в технические логи.
- Проверить резервное копирование и восстановление БД и документов; определить RPO/RTO по требованиям пилота и измерить их на восстановлении.
- Выполнить нагрузочные и конкурентные сценарии. По их результатам оценить синхронный вызов LLM, очередь длительных задач и более узкую блокировку входов расчёта.

**Критерий готовности:** согласован профиль нагрузки и целевые показатели, сохранены результаты измерений и восстановления, пройдены проверки авторизации и изоляции, определены ответственные за инциденты. Количество пользователей, задержки и доступность становятся заявляемыми характеристиками после измерений.

### Этап 5. Валидировать риск и расширять продукты — P2

**Результат для банка:** новые продукты используют согласованные правила, данные и проверенную область применимости модели.

Сначала проверить модель на разрешённой репрезентативной выборке с временным разделением и согласованным определением дефолта. Оценивать качество по горизонтам, калибровку, устойчивость сегментов, дрейф и покрытие признаков. Для трёхмесячного тренда из AUR-17–20 нужен самостоятельный контракт признака и проверка соответствующей модели: в текущем runtime используется тренд за 12 месяцев.

Новые направления — инвестиционный кредит, рефинансирование и следующие продукты исследования — включать после готовности каталога условий, обязательных полей, данных, расчёта и сценариев сотрудника. Залог, поручительство и господдержку развивать как сквозные модули с собственными условиями и источниками. Справочные 16 направлений ассистента задают навигацию, а не подтверждают 16 реализованных кредитных конвейеров.

**Критерий готовности продукта:** согласованные правила и версия условий, воспроизводимый расчёт, сценарии неполных данных и отказов источников, маршрут ручного рассмотрения, проверка клиентского представления и принятия предложения. Для модели — отдельный протокол валидации и решение о допустимой области использования.

### Этап 6. Продолжить путь после принятия предложения — P2

**Результат для клиента:** подписание и выдача становятся видимым продолжением той же заявки.

Сначала спроектировать и проверить моделирование документов, подписания и выдачи внутри кабинета. Отдельно определить основания для реального подписания и платёжной интеграции. Добавить статусы, полномочия, повторяемость действий, ошибки и подтверждение результата источником. Завершение этой работы расширяет текущую границу `offer_status=ACCEPTED`.

**Критерий готовности:** демонстрационный маршрут имеет согласованные состояния и сценарии повторов/отказов; симуляция явно обозначена. Для реального контура нужны отдельные договорённости, интеграции и приёмка — они не следуют из успешной симуляции.

## 3. Как проверять продуктовые гипотезы

Ниже — предлагаемые критерии пилота, а не уже достигнутые показатели. До начала исследования согласовать выборку, одинаковые условия заданий и достаточный объём наблюдений; публиковать числитель/знаменатель и метод расчёта.

| Гипотеза | Эксперимент | Метрика | Предлагаемый критерий и решение |
|---|---|---|---|
| Пользователь завершает анкету без помощи модератора | типовые R01–R03, отдельно ИП и юрлицо | завершение задания, ошибки обязательных полей, число возвратов | ориентир ≥80% самостоятельных завершений; при недостижении переработать основные места затруднений и повторить проверку |
| Ассистент помогает заполнению | сопоставимые задания «форма» / «форма + ассистент», порядок чередуется | медиана времени, ошибки, исправления предложений, завершение | снижение медианы при отсутствии ухудшения корректности; величину целевого эффекта определить после базового измерения |
| Подтверждение понятно пользователю | попросить проверить предложение, затем изменить один реквизит | правильность объяснения того, что сохранится, и фактическое сохранение | ≥90% верно понимают результат подтверждения; иначе уточнить представление значений и цитат |
| Сотрудник понимает основание расчёта | найти входы, источник, причину и актуальность в подготовленных кейсах | корректность ответа, время поиска, ошибки интерпретации | ни одного случая принятия внутренней рекомендации за опубликованное решение в наблюдаемом задании; ошибки разбираются до расширения пилота |
| Дозапрос сохраняет контекст | сотрудник запрашивает сведения, клиент отвечает текстом/файлом | завершение цепочки, потерянные ответы, лишние повторные обращения | 100% ответов связаны с правильной заявкой и запросом; при несоответствии исправить контракт до пилота |
| Расширение ассистента сохраняет корректные данные | размеченные диалоги, неверные значения и сбои | качество по каждому полю, точность цитат, сохранение соседних полей | все критические отрицательные регрессии проходят; продуктовые пороги качества утверждаются по типу поля, а не одной общей «точности» |

Отдельно вести воронку: создана → сохранена → подана → дозапрос/ответ → решение → предложение принято. Показатели отказа от оформления и времени этапа анализировать по роли, продукту и качеству исходных данных. Из этой воронки нельзя напрямую выводить качество кредитного риска.

## 4. Политика и актуальность

DEMO-политика `AURELIUS_MVP_20261024_V1` действует в дампе по **17.12.2026**. До окончания действия подготовить новую версию параметров, происхождение значений, период применимости и регрессионные сценарии; вводить её отдельным согласованным изменением. Это контроль срока действия политики, а не обещанный релиз на эту дату. Параметры настоящей редакции не меняются этим планом.

При выпуске каждого этапа фиксировать hash кода, версии модели/политики и данных, протоколы, изменённые ограничения и принятое решение о следующем шаге. Подробные основания: [решения](02-decisions.md), [архитектура](05-architecture.md), [тестирование](08-testing.md), [экономическая база](../scoring/main/decision_engine/BASELINE.md).
