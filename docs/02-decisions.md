# 02. Ключевые решения, ограничения и развитие

Сверено по `main` / `a5d90c3` от 26.10.2026. Исправления `c549a06` уже включены: [состав и сверка версий](technical/testing/BRANCH_ALIGNMENT_C549A06.md).

Решения описаны кратко, по схеме «контекст → решение → почему → последствия». Источники:
- решения владельца продукта;
- [Контракт кабинета](history/reports/CABINET_V3.md), [Контракт скоринга](technical/scoring/INTEGRATION.md), [scoring/main/README.md](../scoring/main/README.md);
- журнал решений [Исторический журнал решений](history/architecture/AURELIUS_CREDIT_PROCESS_SUMMARY.md) и история коммитов.

Журнал решений в основном описывает прежние этапы. Здесь отражены только решения, которые действуют в текущей версии.

## Решения

### Р1. Один кабинет поверх существующей БД, служебные данные — в отдельной схеме

- **Контекст.** Бизнес-данные, справочники продуктов, политика и учётки уже лежат в PostgreSQL `business_scoring` (дамп v4). С этой схемой работает скоринг.
- **Решение.** Сервер `personalCab/prom_v2/cabinet_server.py` работает с таблицами `public` из дампа v4 как есть. Сессии, версии, квитанции, журнал, документы, назначения, диалоги и отпечатки расчётов хранятся в отдельной схеме `aurelius_cabinet` (миграции 005–009). Миграции не делают `ALTER`, `DROP` и `TRUNCATE` для `public`.
- **Почему.** Скоринг и кабинет работают с одной заявкой без копирования данных. Схему, на которой обучена и проверена интеграция скоринга, не нужно менять.
- **Последствия.** Повторная инициализация идемпотентна. Действия кабинета пишут настоящие заявки, поля анкеты, решения и предложения в `public`. Прежние серверы (`personalCab/frontend`, `prom_v2.web_server` с БД `aurelius_v2`) в запуск не входят.

### Р2. Скоринг читает финансовые данные только из БД банка

- **Контекст.** В браузере клиент может ввести любые числа.
- **Решение.** Кабинет вызывает `run_application(application_id, save=True)`. Все финансовые входы библиотека читает из БД сама, произвольный контекст из браузера не принимается.
- **Почему.** Риск оценивается по данным банка, а не по заявлению клиента. Анкета клиента сохраняется как `CLIENT` / `UNVERIFIED`.
- **Последствия.** Изменение анкеты не делает сведения клиента проверенными и не меняет записи `companies`. Если в БД не хватает финансовой истории, расчёт возвращает ручную проверку без PD (Р8).

В режиме DEMO отсутствующие ОКВЭД и дата регистрации могут читаться из подтверждённой анкеты конкретной заявки (`application_facts.py`). Они остаются `UNVERIFIED`, не изменяют `companies` и сохраняются в снимке с происхождением. Независимая проверка сотрудником — отдельное действие.

### Р3. Политика скоринга не меняется

- **Контекст.** Политика и модель подготовлены ML-частью команды (`scoring/main`). Кабинет и Docker-запуск подключают их как есть.
- **Решение.** Используются без изменений:
  - метод `annual_pd_limit` из `policy.demo.json`, версия `DEMO_ANNUAL_PD_V2`, минимальное покрытие (DSCR) 1,20;
  - экономические параметры `AURELIUS_MVP_20261024_V1` из `risk_policy_parameters`: спред 1,5 п.п., расходы 2 п.п., маржа 3 п.п., LGD 45%;
  - ключевая ставка 14% из `macro_indicators`.
- **Почему.** Решение владельца продукта. Параметры и их источники задокументированы в [BASELINE.md](../scoring/main/decision_engine/BASELINE.md).
- **Последствия.**
  - Все значения — допущения демо, а не нормативы банка.
  - Политика в БД действует по 17.12.2026.
  - Результат скоринга на исходных синтетических данных определяется самими данными (см. «Ограничения»).

### Р4. Скоринг не одобряет: решение принимает сотрудник

- **Контекст.** Кейс требует различать скоринговую оценку и кредитное решение.
- **Решение.**
  - Библиотека возвращает только `MANUAL_REVIEW` или `REJECT`, рекомендацию (`POSITIVE`, `NEGATIVE`, `REVIEW_REQUIRED`) и черновик предложения.
  - Статус заявки библиотека не меняет.
  - Решение `APPROVE`, `REJECT` или `REQUEST_DATA` принимает ответственный сотрудник, причина обязательна.
  - Одобрить можно только рассчитанное предложение по актуальному расчёту и без открытых дозапросов.
- **Почему.** В автоматическом режиме часть входов — приближения (proxy) и индикативная цена; их должен подтвердить сотрудник. Итоговое решение учитывает больше, чем оценку риска.
- **Последствия.** `REJECT` от скоринга — рекомендация, а не отказ. Каждое решение — новая неизменяемая запись `credit_decisions`. Подробно — в [04-credit-process.md](04-credit-process.md#5-скоринг--кредитное-решение).

### Р5. Кто что видит

- **Контекст.** Клиенту нужен понятный результат, а сотруднику — данные для решения. Внутренние оценки риска не должны становиться обещанием клиенту.
- **Решение владельца продукта.**
  - Клиент видит предложение банка (сумму, срок, ставку) и причину отказа, но не видит PD.
  - Сотрудник видит годовую PD, лимит PD и причины.
  - Категории риска и факторы модели не показываются никому.
- **Почему.** Решение владельца продукта. Шкалы категорий риска в скоринге нет (`risk_grade=UNRATED`): границы классов не выдумываются ([scoring/main/README.md](../scoring/main/README.md)).
- **Последствия.** API не передаёт клиенту `assessment` и черновики предложений. Предложение клиент видит только после одобрения.

### Р6. Клиенту показываются только причины сотрудника

- **Контекст.** У скоринга свои коды причин (например, `BANK_CONFIRMATION_REQUIRED`, `MVP_INPUTS_CONFIRMATION`, `DB_INPUTS_UNAVAILABLE`). Они описывают внутреннюю проверку, а не ответ клиенту.
- **Решение.** Серверная проекция `Cabinet.project` оставляет клиенту только точные коды `BANK_APPROVE`, `BANK_REJECT`, `BANK_REQUEST_DATA`, то есть текст сотрудника. Интерфейс (`src/domain/clientReasons.ts`) использует эти сообщения для объяснения результата. Внутренние причины сохраняются у сотрудника.
- **Почему.** Клиенту показывается понятное сообщение о результате рассмотрения.
- **Последствия.** Интерфейс использует сообщения сотрудника для объяснения результата клиенту.

Серверная фильтрация включена в c549a06. Поэтому внутренние причины не передаются клиенту даже при прямом чтении API; договорённость о клиентском представлении действует и на границе сервера.

### Р7. Ассистент только предлагает, клиент подтверждает

- **Контекст.** Клиенту без банковской экспертизы удобнее описать задачу словами. LLM может ошибиться.
- **Решение.**
  - `gpt-oss:20b` через Ollama извлекает сумму, срок, цель, форму бизнеса и девять реквизитов компании в типизированное предложение с дословными цитатами (Pydantic, одна попытка исправления).
  - Явно помеченные реквизиты и однозначные числовые сумма/срок дополняются детерминированным разбором; затем проходят ту же валидацию значений и цитат.
  - В анкету значения попадают только отдельным действием `confirm_facts`.
  - Ассистент работает только в черновике.
  - Справочные вопросы обслуживает RAG по `knowledge/` без изменения заявки.
  - Если модель не ответила, клиент получает 503, а не выдуманный ответ.
- **Почему.** Кейс разрешает только модели с открытыми весами. Роль LLM ограничена извлечением: ставки, PD, решения и переходы определяет код (журнал решений, раздел 12).
- **Последствия.** Форма — источник истины на каждом ходе. Сохранение формы снимает устаревшие предложения ассистента. Диалог приватен для клиента, сотруднику не передаётся.

### Р8. Неизвестное не заполняется догадками

- **Контекст.** Синтетические данные неполные, а внешние источники смоделированы.
- **Решение.**
  - Отсутствующая PD не заменяется нулём.
  - Во время расчёта отсутствующая финансовая история не заполняется нулями. Демонстрационный дамп v4 содержит явно помеченное синтетическое дополнение выручки за сентябрь–октябрь 2025 года.
  - Сбой расчёта или ошибка конфигурации — ошибка сервиса (400, 503), а не кредитный отказ.
  - Отсутствие суммы или срока показывается как отсутствие данных.
- **Почему.** Иначе интерфейс показывал бы результат, которого не было.
- **Последствия.** На неполных данных честный итог — ручная проверка без PD. Трек этапов отмечает этап пройденным только при собственном подтверждении.

### Р9. Демо-учётки и сессии

- **Контекст.** 32 синтетические учётные записи хранятся в `public.user_accounts`; роль и компания определяются сервером.
- **Решение.** Сессионный токен хранится как хэш; cookie имеет `HttpOnly`, `SameSite=Strict`, `Path=/api/v2`, срок 8 часов. POST проверяется по `Origin`. Пароль не возвращается в API и не пишется в логи.
- **Последствия.** Для демонстрации учётки получают из запущенной БД по инструкции [09](09-deployment.md#5-проверка-готовности).

### Р10. Предложение действительно только для данных, на которых рассчитано

- **Контекст.** Между расчётом, одобрением и принятием данные компании, продукта или политики могут измениться.
- **Решение.** Кабинет хранит отпечаток всех входов расчёта и связывает его с решением сотрудника и предложением. Если при одобрении или принятии данные изменились:
  - одобрение отклоняется с `SCORING_STALE`;
  - принятие отклоняется с `OFFER_STALE`: предложение снимается, заявка возвращается на рассмотрение.
- **Почему.** Согласованный контракт актуальности ([CABINET_V3.md](history/reports/CABINET_V3.md)).
- **Последствия.** Снятие предложения — техническое действие, а не отказ. На время проверки таблицы источников блокируются; это локальная сериализация обработки.

### Р11. Ответственный сотрудник

- **Контекст.** Заявку не должны одновременно решать двое.
- **Решение.** Сотрудник берёт заявку в работу (`claim`). Скоринг, проверки и решение доступны только ответственному. Освободить заявку может только он сам. Общую очередь видят все сотрудники.
- **Почему.** Решение владельца продукта, в том числе для старых заявок без назначения.
- **Последствия.** Двойное назначение исключено блокировкой строки и проверкой версии. Назначения и освобождения пишутся в журнал.

### Р12. Проверка сотрудника не исправляет исходные данные

- **Контекст.** Сотрудник проверяет полномочия подписанта или расхождение выручки по документу.
- **Решение.** `verify` сохраняет вид проверки, источник, комментарий, автора и время в журнале. Данные компании и поля анкеты не меняются и не становятся `VERIFIED`.
- **Почему.** Решение владельца. Исправление исходных данных требует отдельного процесса, который пока не подключён.
- **Последствия.** Этап «Данные подтверждены» в треке на новых заявках не отмечается.

### Р13. Документы хранятся в БД без извлечения данных

- **Решение.**
  - PDF и CSV до 10 МиБ сохраняются в `aurelius_cabinet.documents` вместе с SHA-256, автором и привязкой к заявке и дозапросу.
  - Проверяется только формат: заголовок и конец PDF; UTF-8 и одинаковое число колонок в CSV.
  - Статус документа — `STORED_UNVERIFIED`.
- **Почему.** Для извлечения данных в признаки модели нужен отдельный проверяемый контракт.
- **Последствия.** Документ видит сотрудник, но скоринг его не использует.

### Р14. Сценарий заканчивается принятием предложения

- **Решение.** В текущей версии путь завершается принятием предложения клиентом (`offer_status=ACCEPTED`). Подписание документов и выдача средств не реализованы, даже в виде симуляции.
- **Почему.** Обязательный результат MVP — прохождение заявки до результата рассмотрения. Кейс разрешает моделировать подписание и выдачу, но это расширение основного сценария.
- **Последствия.** Mock-режим фронта с имитацией подписи и выдачи к текущей версии не относится.

### Р15. Три продукта в заявке, 16 направлений в подборе

- **Контекст.** Исследование описывает 11 типовых кредитных сценариев и 2 сквозных модуля. Каталог ассистента — 16 направлений.
- **Решение.** Заявка в БД поддерживается для R01, R02, R03. Остальные направления помечены как неподдерживаемые и не подменяются обычным кредитом.
- **Почему.** Завершить оборотный путь целиком раньше, чем расширять каталог. Бизнес-БД содержит условия только R01–R03.
- **Последствия.** Другие продукты — план развития.

### Р16. Воспроизводимый запуск

- **Решение.**
  - Один Compose-проект: PostgreSQL 17 с однократным восстановлением дампа в пустой том, `init` со сверкой дампа и миграциями, `model-init` с проверкой генерации модели, кабинет.
  - Внешний Ollama используется, если доступен, иначе встроенный.
  - Версии закреплены: `requirements.lock.txt`, `package-lock.json`, digest образа Ollama.
- **Почему.** Требование кейса: единый способ запуска на обычном ПК без платных ресурсов.
- **Последствия.** Кабинет не стартует без готовой модели. Подробно — [09-deployment.md](09-deployment.md).

## Ограничения текущей версии

| Граница | Описание |
|---|---|
| Данные и внешние источники | синтетические данные в БД; интеграции описаны в [THIRD_PARTY_NOTICES](../THIRD_PARTY_NOTICES.md#смоделированные-интеграции) |
| Модель и политика | DEMO на синтетических данных; параметры не являются нормативами банка |
| Подписание и выдача | реализованный путь завершается принятием предложения |
| Документы | PDF/CSV хранятся как `STORED_UNVERIFIED`; данные из них автоматически в признаки не извлекаются |
| Проверки сотрудника | сохраняют источник, автора и комментарий; не меняют профиль `companies` |
| Повторный расчёт | после ответа на дозапрос запускается сотрудником |

## План развития

Следующий результат — устойчивый демонстрационный контур и проверка удобства по обеим ролям. Затем — расширение источников и проверяемого извлечения, подготовка управляемого пилота, валидация риска и новые продукты. Моделирование подписания и выдачи продолжает текущий путь после принятия предложения.

В [основном roadmap](10-roadmap.md) для каждого этапа указаны польза, зависимости и критерии готовности, отдельно — предлагаемые эксперименты и контроль срока действия политики 17.12.2026. Порядок — редакционное предложение для дальнейшего планирования. Уже включённое исправление c549a06 отражено в текущей базе, а не в списке будущих функций.

Полные записи с контекстом, альтернативами и свидетельствами реализации — в [16 ADR](extended/decisions/README.md).
