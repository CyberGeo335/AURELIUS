# Клиентский вход и проверка изменений

В PostgreSQL схема `aurelius_workflow` содержит `client_accounts`: ФИО,
уникальный логин, PBKDF2-SHA256 хеш пароля с индивидуальной солью и уникальный
`company_id` с внешним ключом на `public.companies`. Один клиент — один бизнес.
Идентификатор бизнеса назначает сервер после входа; чат и `/api/context` не могут
сменить его. Сессия действует 8 часов, выход отзывает её. Вход ограничен 10
попытками в минуту с адреса. HTTP и cookie рассчитаны на локальный DEMO.

Миграции добавочные, существующие бизнесы и тома сохраняются. Подготовка новых
синтетических учётных записей выполняется явно, после настройки PG-переменных:

```sh
PY=/Users/retro0/projects/PyVenv/venv_core/bin/python
$PY -m personalCab.prom.prom_lab.ai_agents_lab.database --init-workflow
$PY -m personalCab.prom.prom_lab.ai_agents_lab.database --seed-clients --credentials-output /private/tmp/aurelius-client-credentials.json
```

Создаются 30 записей `client01`–`client30` для первых 30 существующих бизнесов.
Пароли случайные. Выходной JSON содержит ФИО, логин, выданный пароль и ID бизнеса;
он создаётся с правами 0600 вне репозитория. Повторная подготовка не сбрасывает
пароли и не меняет привязки; для повторного запуска нужен новый выходной файл.
Нельзя запускать подготовку на реальных данных под видом синтетических.

Для текущего локального стенда список уже выданных реквизитов сохранён в
`personalCab/prom/prom_lab/ai_agents_lab/data/client_credentials.json` (0600).
Этот каталог исключён из Git и Docker build context.

Кабинет доступен по адресу http://127.0.0.1:5173/. PostgreSQL-режим требует входа.
Анонимный SQLite сохранён только для совместимости и тестов.

Корректное значение становится актуальным **заявленным** значением заявки.
Оно не получает статус проверки по реестрам. Неверное значение не заменяет
известное: LLM получает одну попытку исправления извлечения, затем клиенту
задаётся вопрос. ИНН независимо проверяется по исходному сообщению, чтобы LLM
не могла обрезать лишние цифры. Анкета проверяет SQL-типы, ИНН (10/12 цифр с
учётом формы), ОГРН (13), ОГРНИП (15), КПП (9). Произвольный текст `format_rule`
не исполняется как код. Проверки контрольной суммы ИНН нет: достоверность
проверяет сотрудник по реестру.

Изменения параметров хранятся в `credit_cases.payload.client_changes`, изменения
анкеты — в `client_field_changes`. Есть старое и новое значения, ревизия и время.
Они подсвечиваются в общем логе/анкете и передаются в пакет M5 как
`client_changes` с причиной `CLIENT_DATA_CHANGED_CHECK_REGISTRIES`.
Очередь сотрудника доступна только через доверенный операторский CLI:

```sh
$PY -m personalCab.prom.prom_lab.ai_agents_lab.operator client-changes --reviewer bank-operator
# Можно ограничить очередь: --case-id CASE-...
```

Проверка поля анкеты выполняется существующим `verify-field` с явными `value`
и `source_ref`; соответствующая запись очереди получает `REVIEWED`.
Клиентские API не подтверждают данные и не принимают кредитные решения.
Старые снимки и исходные реестровые сведения остаются неизменными.
