## Запуск и откат

```sh
docker compose -p aurelius-v2 -f compose.v2.yaml up --build -d
```

Открыть http://127.0.0.1:5180/. Клиенты `client01`, `client02`; сотрудник `analyst`. Публичный пароль синтетического DEMO: `Aurelius2026!`. Аккаунты создаются только явным seed-demo в init; повтор не меняет пароль. Сессионные токены хранятся в БД как SHA-256, cookie HttpOnly/SameSite=Strict, срок восемь часов; выход отзывает сессию. Вход ограничен десятью попытками за минуту с адреса.

V2 использует собственные Compose project/том/БД **aurelius_v2**. Рабочие ресурсы V1 не изменяются. Импорт кейсов V1 или localStorage не выполняется. Bootstrap synthetic backup запускается только при пустом томе; init применяет добавочные миграции. Интегрированный сервис отказывается работать в базе с иным именем, чтобы исключить случайные бизнес-записи в V1. V2_POSTGRES_PASSWORD задаёт пароль локальной БД; демонстрационное значение публично. Реальные внешние банковские действия не выполняются.

Откат интерфейса: продолжать пользоваться прежним V1 :5173 или mock WEB :5175. Остановка V2 — `docker compose -p aurelius-v2 -f compose.v2.yaml stop`. Не удалять volumes ради обновления.

## Архитектура

`personalCab/web/src/app/IntegratedCabinet.tsx` — отдельное серверное представление WEB с существующими стилями/компонентами V2. `VITE_API_MODE=http` выбирает его; автономные mock-экраны остаются доступны в исходном режиме. Это функциональная серверная компоновка, а не заявление о визуальном совпадении всех прежних макетов/пошаговых экранов. `HttpV2Api` не подставляет синтетические данные при ошибке API.

`web_server.py` обслуживает собранный SPA и session API на одном origin. Его cookie-сессии независимы от старого технического token gateway. Команда имеет явный case_id/expected_version; URL сохраняет выбранный кейс. Browser storage не является владельцем заявки. Общие операции имеют request_id и собственный receipt; неизвестный сетевой исход повторяется с прежним payload. Исправленное содержимое получает новый ID.

`integration.py` переиспользует бизнес-сервисы первой версии как библиотеки **внутри отдельной базы V2**. Их совместимые service_case-записи находятся в aurelius_workflow этой отдельной БД; доменное состояние нового агента — aurelius_agent_v2. Это не запись в runtime V1. Сохранение кейса, service_case, бизнес-записей, receipt и аудита объединено одной транзакцией через thread-local connection. M3 читает исходные данные отдельной read-only repeatable-read транзакцией, затем сохраняет неизменяемый snapshot в общей записывающей транзакции.

## Доступные сценарии

- Серверный вход/выход/восстановление; отдельные клиентские компании и роль сотрудника.
- Создание нескольких кейсов, форма запроса, явный выбор продуктового кандидата из каталога; чат с предложением фактов, подтверждением и RAG с источниками.
- Пять отдельных часовых разрешений, отзыв, проверка перед зависимым действием. Фраза в чате не выдаёт разрешение.
- M3: получение snapshot, адресная анкета, клиентские UNVERIFIED-ответы, загрузка содержимого файлов в PostgreSQL, hash и извлечение; исходные финансовые строки не возвращаются в общий state UI.
- M4: настоящий зарегистрированный CatBoost после явного сохранения проверенного FeatureInput сотрудником. Без него — INSUFFICIENT_DATA/null; для неподдержанной модели — явный статус. PD и факторы mock не используются.
- M5: подача, ручные OFFERED/DECLINED/REQUEST_DATA, явные условия/ставка/комиссии/expiry, график, отдельный DEMO-акцепт и исполнение. R01 — выдача, R02/R03 — открытие лимита. При нулевых комиссиях R01 — идемпотентные платежи DEMO.
- Сотрудник получает очередь и досье, проверяет поля с source_ref, сохраняет проверенные модельные входы и решение. Все изменяющие reviewer-действия проходят `prom_v2/operator.py` и серверную роль OPERATOR; borrower не может вызвать их прямым HTTP.

Не вводились автоматическое одобрение/отказ по синтетическому PD, новые финансовые формулы, production IAM, юридические подписи или реальные переводы. Модельные входы пока задаются явно: отсутствие автоматического mapping не скрывается демонстрационными значениями. Утверждённая policy/продуктовые условия не выдумываются; UNKNOWN допустим. Это сохраняющиеся границы DEMO, а не отключённые адаптеры.

## API

| Путь | Назначение |
| --- | --- |
| POST `/api/v2/login`, `/logout` | Проверка пароля / отзыв cookie-сессии |
| GET `/api/v2/session`, `/state` | Доверенная личность, разрешённые кейсы, компании и grants |
| POST `/api/v2/action` | request_id + kind: command, consent, fields, document, payment либо доверенные features/verify/review |

`kind=command` содержит V2 Command. Остальные кейсовые действия требуют case_id/expected_version. Сервер определяет owner/company/role, проверяет актуальную сессию, scope, стадию и доступ. Переиспользование ID с другим содержимым или устаревшая version дают 409. Данные формы не могут предоставить operator-права.
