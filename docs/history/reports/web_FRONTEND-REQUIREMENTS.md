# AURELIUS — функциональные требования к интерфейсу

Выборка из документа «AURELIUS — функциональные требования MVP» (версия от 24.10.2026): только то, что должно быть **видно и работать во фронтенде** — кабинет клиента и рабочее место сотрудника банка. Номера требований совпадают с общим документом. Требования бэкенда и ML сюда попали только своей видимой частью (что показать пользователю).

- **Приоритет:** Must — обязательно к показу 26.10; Should — после всех Must; Could — если останется время.
- **Экраны-эталоны:** `screens/01…05` в этой папке (стиль V2, см. `DESIGN.md`). Демо-данные — `DEMO-DATA.md`, поля анкет — `data/application-fields-R01-R03.csv`.
- **Режим данных:** всё ниже должно работать в mock-режиме фронта без бэкенда; ассистент — через существующий `/api/chat`.
- Только десктоп (≥ 1280px), мобильная версия не нужна.

Итого: 74 пункта (75 требований общего документа; PRD-01 и AST-01 повторяются на двух экранах), из них Must — 53, Should — 18, Could — 3.

Один источник правды в коде фронта (`src/domain/status.ts`). Переходы — по схеме состояний из общего документа (STS-01); недопустимые действия в UI недоступны.

| Статус | Клиент видит | Цвет бейджа | Что от клиента |

## 13. Демо-сценарии для проверки (SYS-08)

- [ ] **Через ассистента:** заявка начата в диалоге с ИИ-ассистентом, продукт подобран в чате, заявка доведена в форме с тем же номером.
- [ ] **ИП, одобрение (R01):** анкета → автозаполнение по ИНН → обороты из выписки → лизинг подтверждён → согласия → отправка → живой трек → «Одобрено» → выбор срока → «Принять» → подпись и выдача (демо).
- [ ] **Не хватает данных:** дозапрос → ответ в карточке → та же заявка снова «Проверяем» (ревизия +1); сбой источника виден как ожидание.
- [ ] **Встречное предложение (ООО «Зерно Опт»):** стоп по покрытию → очередь сотрудника → разбор → вариант А с обоснованием → клиент видит предложение и принимает.
- [ ] **Отказ:** понятная причина у клиента, код причины и обоснование у сотрудника.
