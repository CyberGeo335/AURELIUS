# AURELIUS: модули 1–5 в локальном DEMO

Состояние реализации: 24.10.2026. Режим согласован пользователем: настоящий CatBoost на явных входах, ручное решение, оформление и исполнение только в симуляции. Реального банковского API и автоматического решения по синтетической вероятности нет.

## Запуск и обновление

Из корня репозитория, в общей Python-среде:

```sh
/Users/retro0/projects/PyVenv/venv_core/bin/python -m pip install -r personalCab/prom/prom_lab/ai_agents_lab/requirements.txt
/Users/retro0/projects/PyVenv/venv_core/bin/python -m personalCab.prom.prom_lab.ai_agents_lab.database --init-workflow
/Users/retro0/projects/PyVenv/venv_core/bin/python -m personalCab.frontend.server --company-id 40 --allowed-company-ids 40
```

PostgreSQL настраивается через `PG_*`/pgpass или `AURELIUS_DATABASE_URL`, Ollama — через `OLLAMA_BASE_URL`. Не передавать пароли аргументами CLI. Для Docker: `docker compose up --build -d`; init применяет все SQL из `scoring/bd/migrations/`, исходный backup восстанавливается только в пустой том. Не удалять существующие тома. В образ включены registry и оба CBM-файла.

`AURELIUS_DEMO_ALLOWED_COMPANY_IDS` задаёт список синтетических компаний, доступных локальному DEMO-профилю; по умолчанию только компания запуска. Это не production IAM. `--database PATH` включает совместимый SQLite-режим М1–М2; новые бизнес-сервисы требуют PostgreSQL.

## Пользовательский путь

В чате доступен [RAG требований](../personalCab/prom/rag/README.md): например, «Какой формат ИНН для R01 ООО?» или «Какие требования к заявке R02 для ИП?». FAISS и подграф LangGraph возвращают выдержки с кодами полей и ссылками на JSON. Для справочных ответов Ollama не нужен. Вопрос не меняет заявку; срок договора связан с `requested_term_months`. Папка `knowledge` включена в Docker-образ.

1. Открыть кабинет. В «Компания, согласия и действия DEMO» выбрать одну разрешённую компанию. Выбор переключает сессию, данные прежнего кейса не удаляются.
2. Выдать нужные согласия отдельными отметками. Каждое действует час, хранится в PostgreSQL и может быть отозвано; startup-флаг не продлевает отозванное согласие.
3. Сформировать запрос в чате или форме. «Мои заявки», форма и чат используют одни серверные кейсы. Название проекта, сумма, срок и цель сохраняются в запросе; сроки договора, транша и выборки разделены. Прежний localStorage не удаляется и не импортируется автоматически.
4. М2 сохраняет все 16 направлений. Для R01–R03 читает PostgreSQL, фильтрует требования ИП/ООО; остальные 13 направлений остаются явными неподдержанными маршрутами бизнес-БД.
5. М3 сохраняет неизменяемые снимки и показывает адресные поля анкеты. Сохранённый ответ получает CLIENT/UNVERIFIED и попадает в `application_field_values`; соответствующий `application_data_requests` закрывается. SQL-типы проверяются, произвольный `format_rule` не исполняется. Для проверки сложных форматов и фактов требуется оператор.
6. Загрузить документы. Файлы сохраняются в PostgreSQL с SHA-256, владельцем, компанией и кейсом. CSV/XLSX извлекаются как таблицы, доступный текст PDF — как текст. Изображения, сканы, старый XLS и зашифрованные PDF требуют ручной проверки. Извлечённый текст не передаётся модели как инструкции и не становится VERIFIED.
7. «Обновить данные и анкету» создаёт новую временную отсечку и снимки. Чтение с отсечкой исключает будущие документы/значения. После уже начатого рассмотрения создаётся новая ревизия; прежние решения/предложения не применяются к ней.
8. Оператор проверяет явные модельные входы командой ниже. «Запустить оценку CatBoost» исполняет М4; без проверенного вектора сохраняется INSUFFICIENT_DATA с null-вероятностью, а не искусственный балл.
9. «Передать оператору DEMO» создаёт ручное рассмотрение М5. Допускается передача неполного досье; неполнота видна оператору и не становится автоматическим отказом.
10. Оператор сохраняет OFFERED, DECLINED или REQUEST_DATA. Пользователь обновляет состояние; предложение содержит явные сумму, срок, ставку в долях, комиссии, условия, срок действия и график.
11. Принятие предложения требует отдельной отметки. Это DEMO-акцепт, не юридическая подпись. Для симуляции исполнения требуется ещё одно отдельное подтверждение. Повтор не создаёт вторую операцию.
12. R01: имитация выдачи и аннуитетный график. R02/R03: только открытие лимита, без имитации выдачи всего лимита. Для нулевых комиссий R01 доступна имитация платежей по графику с идемпотентным operation_id; переплата запрещена. При ненулевых комиссиях нужен отдельный согласованный график их погашения. Просрочки и дефолтные метки не выдумываются.

После отмены/завершения можно нажать «Новая заявка». Явная фраза «Новая заявка…» после закрытого обращения также создаёт новую сессию. Старый кейс и аудит сохраняются. Открытую заявку сначала нужно завершить/отменить; существующий кейс можно выбрать в «Мои заявки».

## Доверенные действия оператора

Операторские команды доступны только из локального CLI, а не через HTTP или текст чата. `--reviewer` — обязательный идентификатор человека, действующего в доверенном локальном контуре.

### Явные входы модели

Подготовить JSON с `schema_version`, `kind`, `source_ref`, `currency="RUB"`, `annual_rate_unit="fraction"`, `population="synthetic_sme"` и `features`. Точный набор: `BASELINE_FEATURES` (16) / `DYNAMIC_FEATURES` (23) в `services/data_preparation.py`. Пропуски, NaN, лишние признаки, неизвестные категории и неявные единицы отвергаются. Сумма, срок и форма обязаны совпадать с текущим запросом. Никакие ratios не выводятся из БД автоматически без методологии.

```sh
/Users/retro0/projects/PyVenv/venv_core/bin/python -m personalCab.prom.prom_lab.ai_agents_lab.operator features --reviewer operator-demo --case-id CASE_ID --product-code R01 --input /absolute/path/features.json
```

Запись привязана к текущим case/revision/evidence/product. После обновления evidence старый вектор не используется. Тестовый синтетический пример есть в `tests/test_cabinet_modules.py:feature_bundle`; он не является рассчитанными признаками компании.

Registry `scoring/models/registry.json` задаёт SHA-256, модель, схему, таргет, стадию, поддерживаемый продукт и сроки обучения (12/18/24/36/48/60 месяцев). Другие сроки не экстраполируются молча. Baseline выдаёт `CUMULATIVE_PD` на горизонте (по умолчанию 12 месяцев, не длиннее срока), dynamic — `ONE_MONTH_HAZARD`. Сохранены полный вектор, происхождение, registry/model hash и снимки. Отдельного обученного калибратора нет; вероятность не выдаётся за валидированный российский PD12. Для R02/R03 модель вернёт UNSUPPORTED_MODEL, после чего доступно ручное рассмотрение. Публикация dynamic hazard в `public.scoring_results.pd` запрещена: там null, точная семантика хранится в `assessments.data`.

Опциональный `cashflow_scenario` содержит явно подтверждённые `cfads_monthly_rub`, `existing_debt_service_monthly_rub`, `source_ref`, `basis_version`, список `stress_cfads_monthly_rub` и известные `fees_rub` (либо null). М4 рассчитывает аннуитетный платёж и DSCR по явно заданным месячным величинам, не выводит CFADS из выручки и не применяет придуманный порог. Неизвестные комиссии остаются null. Расчёт иллюстративный, решение остаётся ручным.

### Подтверждение условий продукта

`approve-product --terms-id ID --input approval.json --reviewer operator-demo` принимает явные `policy_version`, `effective_from`, `effective_to`, `source_checked_at` и `rule_mappings`. Каждое отображение задаёт поле запроса и `verified_only`; порог и оператор сравнения читаются из конкретной SQL-версии правила. Единицы не конвертируются автоматически. До подтверждения условий или при отсутствии отображения проверки остаются UNKNOWN. Неуспех REVIEW/INFORMATION-условия не исключает маршрут как блокирующий отказ.

### Устранение конфликтов и проверка анкеты

`resolve-profile --company-id ID --input resolution.json --reviewer operator-demo` принимает `legal_form` (IP/OOO/AO/OTHER), `source_ref`, `available_at`. Запись в `profile_resolutions` сохраняет ручное разрешение противоречия; прежние снимки не меняются. После новой отсечки оно заменяет более ранние противоречия, а более поздние конфликтующие источники требуют новой проверки.

`verify-field --case-id CASE_ID --product-code R01 --field-code CODE --input field.json --reviewer operator-demo` принимает `value` и `source_ref`; сохраняет проверенное значение в текущей анкете с BANK/VERIFIED и историей триггера. Самостоятельный ответ клиента такой статус не получает. После проверки обновить данные через интерфейс.

### Ручное решение и предложение

```sh
/Users/retro0/projects/PyVenv/venv_core/bin/python -m personalCab.prom.prom_lab.ai_agents_lab.operator review --reviewer operator-demo --lender-case-id DEMO_ID --decision OFFERED --reason 'Проверено в синтетическом сценарии' --input /absolute/path/offer.json
```

`offer.json`: `amount_rub`, `term_months`, `annual_rate_fraction` (явная доля), `repayment_type` (ANNUITY для R01, LIMIT_ONLY для R02/R03), `expires_at` (будущая дата с часовым поясом), `fees_rub` (явный список, в том числе пустой), `conditions` (явный список).

Для DECLINED/REQUEST_DATA `--input` не нужен; причина обязательна. Устаревшие case/revision/evidence/assessment отвергаются. Предложение, его принятие, исполнение и платежи журналируются в `lender_events`. Ни одна строка public.credit_decisions от DEMO не подтверждает реальное решение банка.

## Контракты API

- `GET /api/chat/state`: история, последний результат и контекст компании/согласий.
- `GET /api/applications`: только кейсы текущего владельца и выбранного субъекта.
- `POST /api/applications/select`: выбрать собственный кейс.
- `POST /api/session/new`: новая сессия после закрытия текущего кейса.
- `POST /api/context`: выбрать компанию только из операторского allowlist.
- `POST /api/consents`: явная выдача/отзыв одного scope.
- `POST /api/chat`: прежний текстовый контракт; роли и согласия в нём не принимаются.
- `POST /api/case/command`: UPDATE_REQUEST, REFRESH_EVIDENCE, ASSESS, SUBMIT, ACCEPT_OFFER, EXECUTE_DEMO, POLL_STATUS. Команда не извлекается из LLM.
- `POST /api/case/fields`: case_id/revision и адресные ответы анкеты.
- `POST /api/documents`, `GET /api/documents`: загрузка и метаданные документов текущего кейса.
- `POST /api/case/payment`: явная имитация платежа с operation_id; реальный перевод не выполняется.

Контекстные команды используют `request_id`, команды workflow — `message_id`. Повтор идентификатора с другим содержимым отвергается. Scope, компания, владелец, ревизия, стадия, текущее предложение и срок действия проверяются сервером. Есть advisory locks, CAS доменного кейса, уникальные ограничения, receipts и журнал событий. Общей транзакции HTTP/LLM/checkpoint/public не предполагается: каждый записывающий сервис обеспечивает повтор без дублирования своего результата.
