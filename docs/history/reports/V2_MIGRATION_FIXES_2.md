# Исправления B05–B14 в интегрированном V2

Дата: 25.10.2026. Продолжение [B01–B04](V2_MIGRATION_FIXES.md) по прямому запросу пользователя. Исправлены перечисленные дефекты; полный перенос всех mock-экранов и финансовые возможности из раздела 3 исходного аудита не объявляются завершёнными.

## Текущие сведения и снимок — разные проекции

В GET `/api/v2/state` у кейса добавлена `current_data`: последние сохранённые `questionnaire` и `documents` с фактическими источниками и статусами. Она читается из PostgreSQL по доверенным owner/company/case. Клиент немедленно видит сохранённое значение и файл, включая период, когда прежний snapshot уже `evidence_stale`.

`data_context` продолжает содержать неизменяемый снимок, использованный для оценки. Последние ответы не переписывают его и не становятся автоматически проверенными. Поля можно сохранять последовательно, даже пока снимок устарел; записи связываются с существующей бизнес-заявкой своего кейса/продукта, а каждое материальное изменение повышает ревизию V2. Чужие и недоступные для редактирования поля сервер отклоняет.

Чтение state объединено одним подключением PostgreSQL; trusted grants клиента загружаются один раз для всей проекции, а не заново для каждого кейса.

## Адресный дозапрос и возврат к проверке

Операторский REQUEST_DATA теперь сохраняет `follow_ups`: конкретные коды полей, имена запрошенных файлов, причину, будущий срок с часовым поясом, полученные ответы и статус OPEN/ANSWERED/SUPERSEDED. Поля выбираются только из текущего досье; файлы указываются обычными именами без путей. Новый дозапрос заменяет прежний открытый запрос, сохраняя его историю.

Клиент видит, что именно требуется и какие части уже получены. Частичный ответ оставляет NEEDS_INFO. После полного ответа:

1. Сохраняются данные и увеличивается revision.
2. Предыдущее assessment/предложение перестают быть текущими.
3. M3 создаёт новый snapshot с уже сохранёнными ответами и файлами.
4. Тот же case_id получает CHECKING; доступны повторная оценка и затем новая подача сотруднику.

Повторная проверка не является автоматическим кредитным одобрением. Для отсутствующего reviewed-вектора M4 по-прежнему возвращает отсутствие оценки; ручное решение требует новой подачи. Старое предложение не возобновляется.

Если сбор источника или сохранение нового snapshot завершается ошибкой, savepoint откатывает только этот сбор. Ответ клиента остаётся сохранённым; кейс показывает CHECKING, `evidence_stale` и понятный `checking_error`. Явный повтор обновления завершает сбор и сохраняет CHECKING. Согласия не выдаются и не обходятся ради такого повтора.

Старый REQUEST_DATA без адресных полей обрабатывается как совместимый запрос дополнительных сведений; следующий содержательный ответ закрывает его. В новом UI оператор обязан выбрать поле/файл и указать будущий срок. Изменение самого запроса/продукта завершает актуальность прежних дозапросов через SUPERSEDED, а не помечает их фиктивно отвеченными. Автоматической отмены из-за истечения срока не вводилось.

## Формы клиента и сотрудника

Анкета и форма проверки сотрудника выделены в `CaseFormsV2.tsx` и привязаны к case_id. Их локальный ввод не переносится в другой кейс. При сохранении анкеты используются базовая version и только изменённые поля; polling не затирает ввод. Незатронутое пустое boolean-поле не мешает частичному ответу.

Сотрудник выбирает поле из досье. Boolean передаётся JSON boolean, целое число — JSON integer, дата — ISO date. Строгая серверная валидация сохранена: строка `"false"` вместо boolean отклоняется. После успешной проверки поле сразу отображается как VERIFIED; обновляется snapshot и инвалидируются прежние производные результаты. Входы модели и ручные решения остаются за операторской границей.

Исправлен пересчёт зависимой диагностики: возврат допустимой формы бизнеса снимает устранённый CONFLICT ИНН. Повтор прежнего валидного значения после невалидной попытки снимает соответствующую ошибку и застрявший NEEDS_INFO; независимые ошибки сохраняются.

## Доступные действия и результат оценки

`Agent.action_denial` используется и при выполнении бизнес-команды, и при построении `allowed_actions`. GET использует актуальные trusted grants; добавлены понятные `action_reasons`. Политика учитывает этап, запрос/подтверждение, продукт, snapshot, открытый дозапрос, наличие оценки/подачи/предложения, expiry и действующие scope.

`allowed_operations` отдельно описывает серверную доступность анкеты, документов, DEMO-платежа и действий сотрудника. UI использует эти списки: недопустимые кнопки отключены, основные причины показаны до отправки. Клиентские и операторские запреты продолжают проверяться на сервере.

Результат M4 отображает реальные probability/kind/horizon, target, model_id, hash артефакта, registry_version и массив reasons. Отсутствующий горизонт явно неизвестен. Ошибки и недостаток входов имеют пояснения; неизвестный код причины не скрывается. Синтетическая модель не объявляется валидированной для реального кредитования; вычисленные объяснения факторов этим этапом не добавлялись.

## Сбои и восстановление операции после перезагрузки

Первоначальные 401 и 503 различаются. Сбой фонового polling виден рядом со временем последней успешной синхронизации, не очищает форму и имеет повтор. HTTP-запросы ограничены по времени; после неизвестного сетевого исхода сохраняется возможность идемпотентного повтора.

Добавлена миграция `003_operations.sql`: закрытый серверный журнал `aurelius_agent_v2.pending_operations`, привязанный к login. Перед изменяющим запросом клиент сохраняет **точный payload с обоими request_id** через POST `/api/v2/operation` (`prepare`). Сам prepare ничего в заявке не исполняет. GET `/api/v2/operations` возвращает только операции текущего аккаунта и признак наличия receipt. Окно восстановления — 8 часов; одновременно допускается до 20 записей.

После reload UI предлагает явное «Восстановить и повторить». Автоматического выполнения нет. Если сервер уже выполнил действие, возвращается исходный receipt; новая заявка/платёж/решение не создаются. После подтверждённого ответа клиент удаляет запись журнала через `acknowledge`. Удаление из списка восстановления само по себе не отменяет ранее выполненное действие; это указано в UI.

Payload документа тоже хранится в PostgreSQL, поэтому восстановление не зависит от лимита browser storage или повторного выбора файла. Browser storage владельцем заявки не становится. При смене сессии локальные данные очищаются, а журнал другой учётной записи не возвращается.

## Внешний порт и Origin

Compose задаёт `V2_PUBLIC_ORIGIN=http://127.0.0.1:${V2_PORT:-5180}`. Host/Origin проверяются относительно явно настроенного внешнего origin, включая его порт; внутренний порт контейнера 5180 не подменяет внешний. Для loopback разрешены соответствующие localhost/127.0.0.1, произвольные origins не разрешены. Некорректный origin приводит к отказу конфигурации.

Проверен отдельный временный контейнер с публикацией `127.0.0.1:5181:5180`: правильный Host получил 200, Host с портом 5180 получил 403. Дополнительно HTTP-тесты проверили отказ чужому Origin. Временный контейнер остановлен и удалён; основной стенд остался на 5180.
