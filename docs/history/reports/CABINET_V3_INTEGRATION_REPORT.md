## Запуск

Задать DATABASE_URL в окружении; установить зависимости scoring/main/requirements.txt
и personalCab/prom_v2/requirements.txt. Затем:

```sh
PY=/Users/retro0/projects/PyVenv/venv_core/bin/python
$PY -m personalCab.prom_v2.cabinet_server --init
cd personalCab/web
npm ci
VITE_API_MODE=http npm run build
cd ../..
$PY -m personalCab.prom_v2.cabinet_server
```

Открыть http://127.0.0.1:5173. Ollama/gpt-oss:20b запускать отдельно;
OLLAMA_BASE_URL меняет адрес сервиса. --init выполняет только миграции 005–009
отдельной схемы. Не запускать старый web_server и не восстанавливать дамп
поверх существующей базы. Подробный контракт — [CABINET_V3.md](CABINET_V3.md).

## Что остаётся и почему

- Извлечение PDF/CSV в финансовую БД/признаки требует отдельного проверяемого
  контракта; загрузка только сохраняет непроверенный документ.
- Дополнительные сведения о потребности ассистента хранятся в V2-диалоге;
  в анкету переходят только поля с явным существующим соответствием. Ни одно
  сообщение не создаёт финансовую историю или признаки скоринга.
- Изменение исходных реквизитов и финансов сотрудником не подключается:
  согласован только журнал проверки с источником.
- Табличные блокировки консервативны и рассчитаны на локальный DEMO. Для
  production нужен отдельный протокол версий всех источников и инфраструктура.
- 10 PostgreSQL-тестов самого scoring/main требуют другого fixture-контракта;
  они пропущены, новый кабинет проверен на своей полной seeded БД.
- Push остаётся отдельным действием после разрешения владельца.
