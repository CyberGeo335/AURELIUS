# Интеграция PostgreSQL · 24.10.2026

> Актуальное продолжение: [модули 1–5 DEMO](DEMO_MODULES_1_5.md). М4/М5, документы, согласия и единые заявки реализованы в последующем этапе. Ниже сохранён журнал решений и проверок интеграции М1–М3; прежние пометки «не реализовано» относятся к соответствующему этапу.

## Принятые решения

Пользователь подтвердил: сохранить 16 продуктовых направлений, подключить бизнес-БД для R01–R03, перенести workflow/сессии/аудит в PostgreSQL. М3 собирает проверяемый snapshot; неизвестные признаки блокируют готовность, формулы не придумываем и М4 не вызываем. При деплое PostgreSQL поднимается контейнером и автоматически получает исходные данные.

## Запуск

```sh
cp .env.example .env
docker compose up --build -d
```

Кабинет: http://127.0.0.1:5173/. Ollama с `gpt-oss:20b` запускается на хосте отдельно; контейнер обращается к `host.docker.internal:11434`. Все опубликованные порты привязаны к loopback. Это DEMO, перед публичным размещением нужен настоящий контур аутентификации и согласий.

`db` собирается на PostgreSQL 18 (pg_restore поддерживает формат backup 1.16). При **пустом** томе init-скрипт восстанавливает `scoring/bd/business_scoring.backup`; ошибка останавливает инициализацию. Проверено восстановление 30 синтетических компаний (ID начинаются с 40), 3 продуктов и 99 требований. Повторный запуск не восстанавливает backup и не запускает seeds заново. `init` применяет additive SQL `001_workflow.sql` и миграции PostgresSaver; затем запускается `app`. Изменение backup не обновляет существующий том: для последующих данных нужна отдельная проверяемая миграция. Не применять `down -v` к рабочим данным.

Пароль из примера публичный и предназначен только для локального DEMO. Перед деплоем заменить `POSTGRES_PASSWORD`. Компания задаётся доверенной настройкой `AURELIUS_DEMO_COMPANY_ID` (в backup есть 40); браузер её не выбирает. Сбор М3 разрешается только при согласии: `AURELIUS_DEMO_EVIDENCE_CONSENT=true` — явный операторский DEMO-флаг, по умолчанию false. Он создаёт временное серверное согласие для выбранного синтетического субъекта; полноценный интерфейс выдачи/отзыва ещё не реализован.

Для Python на хосте укажите `PG_HOST=127.0.0.1`, `PG_PORT=5433`, `PG_DATABASE=business_scoring`, `PG_USER=aurelius` и пароль через окружение/pgpass. `.env` автоматически читает Compose, Python его не загружает. Общая среда: `/Users/retro0/projects/PyVenv/venv_core/bin/python`.

## Данные и поток

M1 хранит кейсы, ревизии, сессии, квитанции, аудит и checkpoints в `aurelius_workflow`. Сериализация сообщений одного actor защищена PostgreSQL advisory lock; доменный commit атомарно обновляет кейс с CAS, квитанцию и аудит.

M2 сохраняет 16 направлений JSON-каталога. Для term/R01, rcl/R02 и overdraft/R03 читает PostgreSQL terms, eligibility rules, ставки, комиссии, цели, способы погашения и application_field_requirements. Неподдерживаемые направления явно помечаются; требование документа не равно готовому признаку. В backup у terms отсутствуют effective_from/effective_to/source_checked_at, а подтверждение утверждения кредитором вообще не задано в схеме: условия отображаются как справочные, проверки UNKNOWN. Дополнительные eligibility rules перечисляются отдельно с UNKNOWN до согласования семантики и отображений полей.

M3 после согласия читает только выбранную компанию. Финансы/транзакции ограничены датой события и source_checked_at; provenance — obtained_at/verified_at. У текущего company-профиля и долгов нет полного исторического версионирования: snapshot хранит наблюдения с предупреждениями, а не обещает восстановить прошлое. Текущие статусы дефолта/решений/погашений не превращаются в исторические признаки.

Для каждого поддержанного маршрута создаётся собственная **DRAFT** credit_application и неизменяемый MANUAL application_snapshot, связанный с case/revision/route через case_applications. Старые seeded заявки не изменяются. Стабильный hash payload и advisory transaction lock предотвращают повторное создание при повторе; после частичной ошибки следующий запуск переиспользует записанный маршрут. Доменные кейс/receipt/audit фиксируются отдельно от snapshots/checkpoints; общей распределённой транзакции нет. При изменении запроса новая ревизия создаёт новые связи, старые снимки сохраняются.

В единый лог чата входят запрос, кандидаты, требования, company_id, snapshot/application IDs, cutoff и блокировки готовности. Полные строки финансов/транзакций остаются в PostgreSQL, а не в ответе чата. М2 повторно проверяется по разрешённым проверенным фактам того же cutoff. М4 не вызывается.

## Legacy SQLite

```sh
$PY -m personalCab.prom.prom_lab.ai_agents_lab.database --init-workflow
$PY -m personalCab.prom.prom_lab.ai_agents_lab.database --import-sqlite /absolute/path/aurelius.sqlite3
```

Импорт кейсов, сессий, web_clients, receipts и audit выполняется одной транзакцией. Идентичные записи пропускаются, конфликтующие откатывают импорт. Источник открывается read-only и не удаляется. SQLite checkpoints не импортируются: новый PostgreSQL graph начинает команду из доменного кейса. Существующие SQLite-кейсы не имеют доверенной company_id: оператор должен согласовать привязку, до этого нельзя обходить контроль личности. `--database PATH` оставлен только как явно выбранный legacy/test режим.

## Последние правки: Pydantic и адресные уточнения · 24.10.2026

### Что реализовано

- `schemas/resolution.py`: FieldProblem, VerbatimEvidence, BusinessProfileResult/VerifiedProfileFact, DataGap и DataResolutionPlan. Контракт явно различает MISSING/INVALID/UNGROUNDED/CONFLICT/UNAVAILABLE/UNCONFIGURED и ASK_USER/DATABASE_THEN_USER/ENGINEERING. План хранится с кейсом, входит в DialogueResult и единый лог.
- `services/extraction_validation.py`: каждое поле patch проверяется отдельно через Pydantic. Сумма/срок — положительные целые, bool/строки/дроби в качестве суммы отвергаются. Проверяется дословная цитата текущего сообщения; однозначные числовые цитаты с единицами дополнительно сверяются со значением. Общая фраза «на товар» не подтверждает разовость/повторяемость.
- Явно недопустимые числовые команды изменения суммы/срока проверяются кодом даже при null от LLM: такое изменение нельзя молча проигнорировать. Проверка не подставляет положительные числа вместо модели.
- Сохранена одна repair-попытка. Корректные соседние поля не пропадают из-за ошибки одного поля, пропуска при repair или отказа транспорта на repair. Разные валидные значения одного поля в двух попытках дают CONFLICT. Диагностику формирует код, а не LLM.
- `services/data_resolution.py`: вопросы детерминированы по действительно отсутствующим или спорным полям. Незавершённые уточнения переживают STATUS и перезапуск; новый корректный ответ снимает соответствующее замечание. Невалидная новая сумма не перезаписывает предыдущую и блокирует дальнейшее продвижение до уточнения.
- `lookup_business_profile` — отдельный read-only tool оркестратора до готовности всего запроса. Проверяет actor/company/borrower, полномочия и EVIDENCE_COLLECTION consent. Запрашивает только форму/тип компании, source_checked_at и provenance, без банковских транзакций, скоринга и старых сумм/сроков.
- Форма бизнеса заполняется только из согласованных VERIFIED provenance с корректными company_id/borrower_id и временной отсечкой. При отсутствии подтверждения, конфликте или ошибке БД задаётся вопрос. Отсутствие согласия не блокирует самостоятельный ответ пользователя и не инициирует запрос бизнес-данных. Runtime-хранилище PostgreSQL при этом необходимо: глобальная недоступность PostgreSQL по-прежнему означает STORAGE_UNAVAILABLE.
- M3 учитывает противоречащие provenance по форме; такие сведения не объявляются проверенными. Условия продуктов без актуальности и неутверждённые mapping/формулы ML помечаются ENGINEERING. Ответы клиента не утверждают банковские условия и не устраняют отсутствие модельной методологии. М4 остаётся выключенным.

### Что ещё не реализовано / что сделать

1. Расширить подтверждённый DB lookup за пределы legal_form только после согласования источников, правил свежести, единиц и преобразований. Возраст, оборот, collateral и ratios сейчас не заполняются произвольными SQL-агрегатами. Цель, сумма и срок нового запроса не берутся из прошлых заявок.
2. Добавить регрессионный eval-набор на русском языке: словесные числа, диапазоны, несколько сумм, отрицания, вложенные цитаты, несколько субъектов/целей. Pydantic гарантирует контракт, но сам по себе не доказывает смысловую истинность произвольного ответа LLM. Транспортные ошибки и полностью некорректный JSON по-прежнему возможны.
3. Уточнить долговременную provenance-модель каждого request-поля и сроки свежести. DB lookup использует cutoff текущей ревизии; автоматическая переоценка ранее неизвестного значения по новым источникам без новой отсечки не реализована.
4. Реализовать IAM, UI/реестр согласий и отзывов, загрузку/проверку подтверждающих документов. Простое сообщение пользователя не становится VERIFIED и не исправляет противоречие в источнике.
5. Утвердить product approval/version/dates и дополнительные eligibility rules; формулы и PostgreSQL→16/23 mapping; затем реализовать М4/политику и М5. Ограничения предыдущего раздела сохраняются.
