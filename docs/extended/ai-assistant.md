# Ассистент: проверяемое предложение изменений

## Роль в работающем кабинете

Ассистент помогает заполнить черновик и отвечает на вопросы о требованиях. [cabinet_assistant.run_dialogue](../../personalCab/prom_v2/cabinet_assistant.py) связывает граф Agent V2 с конкретными application_id, user_id и company_id из серверной сессии. Внутрь графа допускаются только CHAT и CONFIRM_FACTS. Команды согласий, отправки заявки, решения и исполнения из прежнего общего Agent API этой границей не подключены.

Вход: текст до 12000 символов, актуальные поля формы, выбранный продукт, история клиента и версия заявки. Выход: история, problems и pending с proposal_id, patch, clear_fields, quotes, source_message_id/source_text и display_values. Это предложение, а не подтверждённые финансовые данные. Сумма/срок/цель отображаются в анкете; характер потребности может остаться контекстом диалога.

## Обработка одного хода

1. Cabinet проверяет роль, владение, DRAFT, expected_version и request_id. Диалог читается из PostgreSQL с блокировкой строки.
2. Сохранённая форма заново проецируется в LoanRequest. История чата не подменяет актуальные поля и не переносит сумму из прежних заявок компании.
3. [LangGraph](../../personalCab/prom_v2/agent.py) выполняет route → execute → project. Справочный маршрут [RequirementsRAG](../../personalCab/prom/rag/pipeline.py) ограничивается выбранным продуктом и формой бизнеса; он не меняет анкету. Retrieval использует TF-IDF слов/символьных n-грамм и FAISS IndexFlatIP в памяти; ответ собирается из требований без генерации LLM.
4. [OllamaExtraction](../../personalCab/prom_v2/adapters.py) вызывает gpt-oss:20b через структурированный JSON schema, temperature=0, num_ctx=16384, num_predict=4096, timeout=120 секунд; передаются последние восемь сообщений с ограничением длины.
5. `declared_facts` детерминированно дополняет явно заданные реквизиты и однозначные сумму/срок. `checked_extraction` независимо проверяет значения и дословное основание в текущем сообщении. Pydantic задаёт структуру, но не заменяет проверку доказательств.
6. При диагностике допускается одна попытка исправления. `merge_repair` сохраняет уже корректные поля. Непроверяемый результат не становится сохранённым фактом.
7. CHAT сохраняет историю и pending. Отдельный confirm_facts с актуальным proposal_id переносит принятые поля в public-форму через cabinet.save. Проверяются совпадение ИНН с компанией и совместимость правовой формы. Удаление полей требует формы.

Источник контракта реквизитов — [declared_facts.py](../../personalCab/prom_v2/declared_facts.py). Они сохраняются в анкете с происхождением CLIENT/UNVERIFIED, а не исправляют профиль companies. Сохранение формы снимает устаревшее предложение. Свой диалог клиент видит после обновления страницы; сотруднику dialogue не передаётся.

## Пример: сообщение → предложение → подтверждение → значение

Ниже авторская иллюстрация контракта, **не лог запуска**. UUID и версия условны.

| Шаг | Действие | Проверяемый результат |
|---|---|---|
| Сообщение | «Сумма 1000000 рублей, срок 12 месяцев» | action=chat, форма ещё прежняя |
| Предложение | pending.patch: amount_rub=1000000, term_months=12; quotes с точными фрагментами сообщения | отображены значения и кнопка подтверждения |
| Подтверждение | action=confirm_facts, proposal_id текущего pending, expected_version из state, новый request_id | сервер проверяет актуальность и владение |
| Сохранённое значение | requested_amount=1000000, requested_term_months=12; поля R01_05/R01_06 для R01 | повторное чтение state возвращает эти значения; companies не меняется |

Проверенный материал — [протокол AUR-01–10](../technical/testing/LLM_SCENARIOS_01_10_RESULTS.json) и [методика](../technical/testing/LLM_SCENARIOS_01_10_FIXES.md): 10 сценариев на изолированной v4, реальный HTTP и Ollama, расчёт присутствует и компании неизменны во всех десяти. JSON фиксирует итоговые поля и флаги, но не полный текст каждого хода: его нельзя превращать в дословные диалоги. Тест `test_v2_dialogue_confirmation_form_sync_and_isolation` в [test_cabinet.py](../../personalCab/prom_v2/tests/test_cabinet.py) проверяет связь подтверждения и формы; тесты с детерминированным extractor не доказывают качество живой LLM.

## Контрактный диалог, зафиксированный в тесте

В `test_v2_dialogue_confirmation_form_sync_and_isolation` задан точный сценарий с детерминированным extractor, а не живой моделью. Исходно сохранён срок 24 и цель «Моя сохранённая цель».

| Шаг | Вход / ожидание проверки |
|---|---|
| Сообщение | «ООО нужно 1500000 рублей на 36 месяцев» |
| Предложение | amount_rub=1500000, term_months=36, legal_form=OOO; цитаты «1500000 рублей», «36 месяцев», «ООО» |
| До подтверждения | requested_amount=NULL, requested_term_months=24; повтор request_id не дублирует сообщение |
| Подтверждение | confirm_facts с текущим proposal_id |
| Сохранено | requested_amount=1500000.00, term=36, R01_14=ООО; цель не изменилась, статус DRAFT, consentData не включено |
| Проверка устаревания | после нового save прежний proposal_id даёт STALE_PROPOSAL |

Это проверенные утверждения исходного теста; новый прогон этого теста при подготовке не выполнялся.

## Ошибки и границы полномочий

Недоступность или непроверяемый ответ модели даёт 503 EXTRACTION_UNAVAILABLE. Ветка ошибки не добавляет выдуманную историю; клиент продолжает формой или повторяет запрос. Неверный proposal_id — 409 STALE_PROPOSAL; неверная версия — 409 STALE_CASE_VERSION. Повторы обслуживаются общими receipts кабинета, а не памятью модели. Доступность RAG и извлечения зависит от их реальных зависимостей; справочный маршрут не следует считать универсальным резервом при любом отказе Ollama.

Согласия проверяются при подаче сервером; просьба в тексте не включает их. PD, ставка, публикация и решение определяются скорингом и сотрудником. Набор команд Agent V2 шире работающей границы кабинета: наличие команды в enum не означает доступную функцию в HTTP. План оценки precision/recall, корректности цитат и успешного подтверждения — [roadmap](roadmap-and-validation.md).
