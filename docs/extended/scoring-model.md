# Карточка загружаемой модели dt_monotone_v1

## Назначение и идентичность

Модель оценивает условную месячную вероятность события в синтетическом кредитном эпизоде. Она входит в расчёт риска и черновых условий, а итоговое кредитное решение принимает сотрудник. Загружается CatBoost из [model/](../../scoring/main/ml_scoring/model/README.md); SHA256 файла `best_model.cbm` — `1e729ce490ba9ce67b69abae6730fed469b5e13db7107348634d46cd2859472b`.

[Predictor](../../scoring/main/ml_scoring/predictor.py) проверяет наличие артефактов, порядок имён признаков и контрольную сумму из best_config. Serving-версия дополняет имя первыми 16 символами SHA256. Файлы модели, features и best_config передаются вместе. Экспериментальные динамические модели не загружаются этим контрактом.

## Данные, единица наблюдения и обучение

Исследовательское происхождение — [подготовка survival](../../scoring/notebooks/01_prepare_survival.ipynb) и [обучение survival](../../scoring/notebooks/02_train_survival.ipynb). Для текущего обучения используется `data/processed/ml_survival_dataset.parquet`, сохранённый split `models/experiments/survival_v3_baseline/splits.npz`. SHA256 split в конфигурации: `fc2f4ad3fd559ef8ad2aa64a195cb94285ef947096be56414f0ceb3e345f0bcf`.

Единица исходной выборки — эпизод с `duration`, `event`, `term_months`; единица обучения — месяц наблюдения эпизода. `expand` создаёт строки до наблюдаемой duration. Положительная метка только у последнего месяца, если event=1; цензурированные эпизоды не превращаются в известные дефолты. Определение экономического события в генераторе требует сохранения вместе с датасетом: это синтетический таргет, не подтверждённая разметка банковской просрочки.

В `best_config.json`: исходный train — 140000 эпизодов, обучающая подвыборка — 35000 с seed 20261024, validation — 30000. Кандидат выбирался по исходной validation, не по 30 демонстрационным компаниям. Test оценивается отдельным validate_monotone_release после фиксации кандидата. Исходный test уже использовался для прежней модели, поэтому это не новый внешний holdout. В [генераторе v2](../../scoring/data/generators/generate_survival_v2.py) событие default_event моделируется случайным испытанием с hazard, зависящим от финансовых траекторий и скрытого качества; это не правило «90 дней просрочки». Случайное цензурирование задаётся censor_at от 7 до 84, наблюдение ограничено также сроком и календарным окном. На каждого синтетического заёмщика генерируется один эпизод. Генератор пишет отдельно статические и dynamic-признаки; динамические current_* не входят в установленную модель.

[Подготовка](../../scoring/notebooks/01_prepare_survival.ipynb) агрегирует первый default_event в duration, при отсутствии события берёт последний наблюдаемый месяц; исходные признаки фиксируются на первом месяце. [Обучающий ноутбук](../../scoring/notebooks/02_train_survival.ipynb) использует GroupShuffleSplit по borrower_id: 70/15/15, seed 42. Это отличается от встроенного хронологического split генератора; train_monotone использует именно сохранённый splits.npz. Без полного манифеста происхождения исходного parquet нельзя объявлять повторную генерацию побитно идентичным восстановлением обучающего набора.

Для отдельного нового исследовательского набора из корня scoring: `python data/generators/generate_survival_v2.py --companies 10000 --output data/research_new --seed 42`. Эта команда не воспроизводит автоматически зарегистрированную модель. Полный генератор и исходные большие данные не обязательны для инференса; доступность каждого входа нужно проверить перед повторным обучением.

## Признаки и происхождение

15 признаков в [features.json](../../scoring/main/ml_scoring/model/features.json); `month_on_book` добавляет predictor, остальные 14 собирает [feature_builder](../../scoring/main/ml_scoring/feature_builder.py).

| Признак | Единица / семантика | Источник |
|---|---|---|
| age_months | полные месяцы возраста | дата регистрации компании / явно помеченный факт заявки |
| industry | retail/services/manufacturing/construction/transport/agriculture | серверный маппинг ОКВЭД |
| entity_type | OOO / IP | companies.entity_type |
| monthly_revenue | RUB за последний полный месяц | только входящие операции REVENUE в RUB |
| revenue_trend_12m | доля: последняя выручка / первая из 13 месяцев − 1 | 13 полных положительных календарных месяцев |
| revenue_volatility | коэффициент вариации, доля | последние 12 полных месяцев |
| operating_margin | доля операционной прибыли в выручке | последняя доступная верифицированная отчётность; proxy денежного потока |
| cash_buffer_months | денежные средства / последняя месячная выручка | отчётность и операции |
| dscr | покрытие существующего месячного обслуживания | max(0, выручка × маржа) / текущие платежи; proxy |
| debt_to_revenue | proxy латентной base_debt генератора | обслуживание долга / (0.16 × историческая средняя выручка), clipping 0.03–3 |

| requested_amount | RUB | сумма кандидата предложения |
| annual_rate | доля годовых | индивидуальная ставка в процентах / 100 |
| macro_stress | синтетический сценарий | явное серверное значение 0, не ключевая ставка |
| month_on_book | номер месяца от 1 | predictor |

`debt_to_revenue` текущего db_proxy_v2/db_auto_v3 не является прямым отношением остатка долга к выручке. Наблюдаемое отношение сохраняется отдельно в financial_observations. DSCR ограничивается 0.05–8, тренд −0.9–3, маржа −0.28–0.48; исходные значения и clipping записываются в feature_adjustments. `current_revenue_trend_3m` не входит в текущие features. Нехватка истории не заполняется нулями.

## Hazard и PD

Для каждого месяца k модель возвращает h(k). Накопленная вероятность к t равна `PD(t)=1−∏(1−h(k)), k=1..t`. Это отличает месячный hazard от вероятности за весь срок. Predictor поддерживает сроки 12,18,24,36,48,60; отчётные горизонты: 12→6; 18→6,12; 24→6,12,18; 36→6,12,24; 48→6,12,24,36; 60→6,12,24,36,48. Это контракт ML, не обещание доступности каждого срока для любого продукта.

## Метрики и критерий принятия

| Выборка | Метрика | candidate | baseline |
|---|---|---:|---:|
| validation | weighted_ipcw_brier | 0.1278136247844353 | 0.1256406842443613 |
| validation | max_calibration_abs_error | 0.02779441700160208 | 0.03689699931318335 |
| test | weighted_ipcw_brier | 0.1303184192979575 | 0.1283363357001039 |
| test | max_calibration_abs_error | 0.02971852511137841 | 0.03746361865440971 |

Источник — строго разделы candidate/baseline [validation_report](../../scoring/main/ml_scoring/model/validation_report.json) и [test_report](../../scoring/main/ml_scoring/model/test_report.json). Числа относятся к синтетической выборке. Меньшее значение обеих метрик предпочтительнее: у кандидата Brier хуже, а максимальная ошибка калибровки test меньше.

Методика [train_monotone.evaluate](../../scoring/main/ml_scoring/train_monotone.py): Brier с IPCW из scikit-survival отдельно по срокам и горизонтам; среднее взвешивается числом эпизодов. Калибровка: в каждой паре срок/горизонт берётся взвешенная по размеру квантильных групп абсолютная разница средней PD и Kaplan–Meier оценки события; max_calibration_abs_error — максимум таких агрегатов по парам срок/горизонт, а не максимум отдельного бина. Это не ROC-AUC и не измеренная доля ошибок одобрения.

Правило выбора: validation Brier ≤ baseline+0.003, максимальная ошибка калибровки ≤0.06 и отсутствие нарушений в проверенной сетке монотонности. В сохранённом validation_report у кандидата нули по всем десяти ограниченным признакам. Ограничения: риск растёт с суммой, ставкой, долговой нагрузкой, просрочкой, волатильностью и stress; снижается с dscr, cash buffer, маржой и трендом. max_ctr_complexity=1 закрывает обход числовых ограничений сложными CTR. Конечная тестовая сетка сама по себе не измеряет качество на реальных клиентах.

## Воспроизведение и связь с политикой

Из корня scoring: `python -m main.ml_scoring.train_monotone`, затем `python -m main.ml_scoring.validate_monotone_release`; продвижение выполняет `promote_monotone.py`. Предварительно нужны parquet, split и исходная baseline-модель по путям в скриптах; при отсутствии их нельзя заменить демо-компаниями. Повторное обучение может зависеть от версий библиотек, контрольная сумма нового бинарного артефакта проверяется отдельно.

Для инференса: `python -m main.pipeline --snapshot main/examples/application.json --policy main/decision_engine/policy.demo.json`. Штатный кабинет вызывает `run_application(application_id, save=True)` и читает БД. Команды здесь описаны по коду, в ходе подготовки документов не запускались.

PD — оценка модели; PD_limit — экономическая граница политики `annual_pd_limit`; recommendation — внутренний вывод о риске и полноте входов; решение APPROVE/REJECT/REQUEST_DATA — действие сотрудника; оффер — отдельные сумма, срок, ставка и график. Поиск условий учитывает платёжеспособность и ограничения продукта, не меняет модель. DEMO-политика `DEMO_ANNUAL_PD_V2`, DSCR 1.20 и параметры экономики в БД не являются нормативами банка. Контракт — [INTEGRATION](../technical/scoring/INTEGRATION.md), развитие проверки — [roadmap](roadmap-and-validation.md).
