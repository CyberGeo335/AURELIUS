# ADR-001: Один кабинет поверх существующей БД, служебные данные — в отдельной схеме

Статус: действует в срезе `68b7b57c0e501e4575bc2a10eee20e6e42f529d4`. Дата принятия и автор ADR отдельно не установлены; развёрнуто 26.10.2026 из решения **Р1**. Это дата документирования, не дата решения команды.

## Контекст и принятое решение

Ниже исходная запись Р1, сохранённая по смыслу и формулировкам; относительные ссылки заменены навигацией к источнику.

- **Контекст.** Бизнес-данные, справочники продуктов, политика и учётки уже лежат в PostgreSQL `business_scoring` (дамп v4). С этой схемой работает скоринг.
- **Решение.** Сервер `personalCab/prom_v2/cabinet_server.py` работает с таблицами `public` из дампа v4 как есть. Сессии, версии, квитанции, журнал, документы, назначения, диалоги и отпечатки расчётов хранятся в отдельной схеме `aurelius_cabinet` (миграции 005–009). Миграции не делают `ALTER`, `DROP` и `TRUNCATE` для `public`.
- **Почему.** Скоринг и кабинет работают с одной заявкой без копирования данных. Схему, на которой обучена и проверена интеграция скоринга, не нужно менять.
- **Последствия.** Повторная инициализация идемпотентна. Действия кабинета пишут настоящие заявки, поля анкеты, решения и предложения в `public`. Прежние серверы (`personalCab/frontend`, `prom_v2.web_server` с БД `aurelius_v2`) в запуск не входят.

## Аргументы

Отдельная служебная схема сохраняет стабильность public и единый идентификатор заявки для кабинета и библиотеки.

## Альтернативы и компромисс

Редакционный анализ при подготовке расширенной документации, не протокол исторического обсуждения команды: Копия бизнес-данных в отдельном workflow-хранилище упростила бы независимость, но потребовала бы синхронизации; текущая схема сохраняет единый application_id.
