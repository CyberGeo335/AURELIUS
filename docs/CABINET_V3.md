# Кабинет с PostgreSQL v3 и scoring/main

Новый HTTP-режим использует существующий React `App` и навигацию. Старые
ServerCabinet, IntegratedCabinet, CaseFormsV2 и web_server сохранены. Для нового
пути запускать **cabinet_server**, а не прежний web_server с БД aurelius_v2.

## Запуск в PowerShell из корня репозитория

Нужны Node >=22.12, Python 3.12 и PostgreSQL 17. В новую пустую business_scoring
восстановить `scoring/bd/v_3 (actual)/business_scoring_wauth.backup` по инструкции
`scoring/main/INTEGRATION.md`. Не восстанавливать поверх существующей БД.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r scoring/main/requirements.txt
# Задать DATABASE_URL в окружении процесса, не сохранять пароль в Git.
# Формат: postgresql+psycopg://postgres:URL_ENCODED_PASSWORD@127.0.0.1:5433/business_scoring
.\.venv\Scripts\python.exe -m personalCab.prom_v2.cabinet_server --init
Set-Location personalCab/web
npm ci
$env:VITE_API_MODE = 'http'
npm run build
Remove-Item Env:VITE_API_MODE
Set-Location ../..
.\.venv\Scripts\python.exe -m personalCab.prom_v2.cabinet_server
```

Открыть `http://127.0.0.1:5173`. Войти логином и паролем из public.user_accounts.
Роль и компания берутся с сервера. Роль, имя и фамилия из формы входа не дают
прав. Cookie HttpOnly/SameSite=Strict хранит токен, сервер хранит только его хэш.
По согласованному демо-контракту пароль сравнивается с user_accounts.password
как есть. Пароль не возвращается в API, не записывается фронтом в хранилища/логи.

Для разработки `npm run dev` запускает Vite на 5174, с прокси к серверу 5173.
Для mock собрать без VITE_API_MODE=http. MockAuthApi/MockCreditApi в HTTP не создаются.

## Что меняется в базе

`--init` выполняет **только** personalCab/prom_v2/migrations/005_cabinet.sql:
создаёт отдельную схему aurelius_cabinet с sessions, application_state, receipts
и events. В ней только служебные данные и FK на существующие public-ключи.
Нет ALTER/DROP/TRUNCATE таблиц public, старых миграций, очистки или перезаписи
данных. Повторный --init идемпотентен. Существующие public FK сохраняются.

Штатные действия кабинета записывают реальные новые заявки, поля анкеты,
историю изменений, подтверждение подачи, решения и статусы офера в таблицы v3.
Редактирование анкеты не делает клиентские сведения верифицированными и не
меняет записи companies: application_field_values получают CLIENT/UNVERIFIED.

## Контракт /api/v2

- POST login: login/password; GET session: публичная серверная личность;
  POST logout: завершение серверной сессии.
- GET state: компании, заявки, требования анкеты и действующий каталог.
  Компания клиента определяется сессией; сотруднику доступна очередь.
- POST action: `{kind:"credit", action, request_id, application_id?, expected_version?, ...}`.
  Действия: create, save, submit, score (сотрудник), review (сотрудник),
  answer, accept, cancel, revise, verify (сотрудник, фиксация источника).
- Методы старого V2 action/command и новый credit-контракт различаются;
  HttpCreditApi использует новый контракт через транспорт HttpV2Api.request.
- Mutations проверяют владельца, роль, версию и request_id. Повтор запроса
  с другим содержимым отклоняется. Подача и receipt сохраняются атомарно;
  после сбоя скоринга повтор того же запроса продолжает расчёт без повторной подачи.
  Сбой расчёта не записывается как кредитный отказ.

## Скоринг и отображение

Новая заявка создаётся DRAFT. Подтверждённая анкета переводится в UNDER_REVIEW
и передаётся внутреннему `run_application(id, save=True)`. Все финансовые входы
читает библиотека, произвольный браузерный context не принимается.
Модель, policy и схема v3 не изменены. Используется DEMO_ANNUAL_PD_V2 с DSCR 1.20
и экономическими параметрами AURELIUS_MVP_20261024_V1 из БД.

Для расчёта нужны реальные входы, перечисленные в INTEGRATION.md. Присутствие
всех полей анкеты не означает наличия 13 месяцев финансовой истории. При
недостатке финансовых сведений показывается сохранённый результат ручной
проверки; PD не заменяется нулём. Данные seed не дополняются выдуманной историей.

Сотрудник видит годовую PD, годовой лимит, единственный офер и reasons.message.
Клиент получает опубликованные сумму/срок/ставку и причины. PD, полный assessment
и offered_conditions не отправляются клиенту. В HTTP нет факторов и категорий
риска, альтернативных демо-расчётов, подписи/выдачи и сброса бизнес-данных.
Сумма/срок/продукт запроса берутся из credit_applications.

Результат библиотеки MANUAL_REVIEW/DRAFT не превращается в одобрение. Сотрудник
подтверждает рассчитанный офер: новая запись решения, APPROVED и PROPOSED.
Клиент принимает конкретный офер: APPROVED остаётся, offer_status=ACCEPTED.
DECISION-снимки не редактируются. После нового расчёта без офера старый успешный
офер не подставляется: используется persistence.offer_id последнего снимка.

## Проверки

```powershell
Set-Location personalCab/web
npm test
npm run build
$env:VITE_API_MODE = 'http'
npm run build
Remove-Item Env:VITE_API_MODE
Set-Location ../..
.\.venv\Scripts\python.exe -m unittest discover -s scoring/main/tests -t scoring -q
# Только отдельная seeded тестовая БД с именем aurelius_test*:
# задать AURELIUS_TEST_DATABASE_URL в окружении
.\.venv\Scripts\python.exe -m pytest personalCab/prom_v2/tests/test_cabinet.py -q
```

На текущем этапе: 84 теста фронта; 8 интеграционных тестов нового backend,
включая реальный CatBoost → решение → акцепт, изоляцию компании, cookie/origin,
неизменность public constraints и повтор после сбоя скоринга. Из 41 существующего
теста скоринга 31 выполнен, 10 PostgreSQL-тестов без отдельной их fixture-базы
пропущены. В браузере проверены вход обоих типов пользователей из восстановленной
БД, новая форма и очередь, десктоп и 390 px. Отдельно в браузере на выделенной тестовой БД выполнены: заполнение новой формы → настоящий скоринг → фиксация источника сотрудником → одобрение → акцепт клиентом; ошибок JavaScript нет.

## Оставшиеся задачи и границы текущего этапа

- По решению владельца ассистент V2 подключается после запуска локального
  Ollama/gpt-oss:20b. В HTTP старый SQLite-чат не показывается. Дальнейший этап:
  серверная привязка case/application/user, извлечение первого запроса,
  подтверждение фактов, доуточнение пропусков и варианты потребностей из каталога.
- Файловое хранилище/загрузка PDF и CSV в новую ветку кабинета пока не подключены.
  Никакая загрузка по одному имени файла не имитируется. Ответ на запрос сейчас
  текстовый и сохраняется в application_data_requests/application_field_values.
- resolveData принимает явный sourceRef: сотрудник фиксирует проверку полномочий
  или расхождения выручки, источник, комментарий, автора и время в служебном
  журнале. По решению владельца это не исправляет исходные данные и не
  делает автоматически VERIFIED финансовые входы модели. Клиент не может
  создавать такие записи и не получает внутренние записи проверки.
- Публичные реквизиты компании не исправляются автоматически из анкеты.
  Процесс принятия таких исправлений сотрудником ещё не подключён.
- Автоматическая проверка изменения внешних финансовых данных между решением
  сотрудника и акцептом требует отдельного контракта актуальности; текущий
  акцепт проверяет владельца, версию заявки и конкретный PROPOSED офер.
- Персональное назначение сотруднику (кнопка «Мои разборы») пока не хранится:
  в новом HTTP-контуре этот экран показывает очередь без обещания назначения.

До первого push требуется разрешение владельца. Этот документ не означает,
что незавершённые пункты выше уже реализованы.
