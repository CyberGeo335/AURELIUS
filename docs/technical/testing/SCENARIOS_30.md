## Версия и метод

- Бизнес-логика: `6a9a4c15a0c0eee4c74a62a1e15b9e5bb704eaf6`; исправление запуска: `68b7b57c0e501e4575bc2a10eee20e6e42f529d4`. Коммит c549a06 в запуск не входил.

- Реальный `cabinet_server.Handler` на локальном HTTP, cookie-аутентификация для каждой компании, Ollama `gpt-oss:20b` на CPU, зарегистрированный CatBoost `dt_monotone_v1_1e729ce490ba9ce6`.
- [Исходный CSV](scenarios30/scenarios_30.csv): 30 строк, компании 35–64. SHA256 загруженного файла с CRLF: `9cd2f608441a3fca8797af024d1d0bef9738c166f1e451b167d895baec4c38b1`. Для версии в Git контрольный hash после замены CRLF на LF — `28ca44722c577a160a82b5d5133b13896108e26568602e6ede09d70ab3f515da`; содержимое строк не изменено. Оба значения сохранены в JSON.
- Для каждой строки создана новая заявка. Сумма 3 млн ₽, срок договора 36 месяцев, цель — пополнение оборотных средств. Для R02 срок транша 6 месяцев, для R03 — 30 дней. Это явные тестовые параметры, а не сведения, извлечённые из старых заявок.
- Прочие обязательные поля заполнены синтетическими ответами через HTTP-форму, согласия и корректность анкеты подтверждены. В AUR-01–09 целевой пропуск не заполнялся формой: помощник запросил реквизит, получил сообщение, сформировал предложение, оно подтверждено отдельным действием.
- Клиентские значения оставались `CLIENT` / `UNVERIFIED`. Результат скоринга считывался в представлении сотрудника. Одобрение, публикация и принятие предложения не выполнялись.

## Как читать финансовые проверки

В AUR-11–16 проверялось направление изменения PD установленной модели при изменении долгового признака, DSCR или денежного резерва. Компания служила собственной базой сравнения: остальные входы фиксировались, выбранный признак сдвигался на половину расстояния к соответствующей границе диапазона генератора. Проверялась нестрогая монотонность — изменение не должно ухудшать направление; возможен неизменный результат на плоском участке модели.

В AUR-19/20 аналогично изменялись совместно DSCR, долговой признак и резерв. Компонент `current_revenue_trend_3m` не проверен: текущая модель использует `revenue_trend_12m`. Поэтому AUR-17–20 имеют статус `PARTIAL`, несмотря на наличие расчёта каждой заявки. Подмена трёхмесячного тренда годовым не выполнялась.

Долговой вход runtime — существующий synthetic proxy `debt_to_revenue`; это не прямой наблюдаемый показатель остатка долга к выручке. Дополнительно сохранено описательное сравнение с медианой контрольных компаний того же продукта. Между компаниями различаются и другие признаки, поэтому это сравнение не доказывает причинное влияние одного фактора.

Названия AUR-07–09 в исходном CSV расходятся с колонками ожидаемого поля. В этом запуске проверены ОКВЭД, дата регистрации и вид деятельности, как указано в ожидаемых проверках; расхождение не скрыто переименованием источника.

## Доказательства и повторение

- [results.json](scenarios30/results.json): выбранные данные сохранённого запуска — входные параметры, ответы ассистента, предложения, подтверждённые значения и provenance, результаты расчётов и PD до/после. Поле `calculated_offer` добавлено при экспорте из сохранённых assessment того же запуска.
- [summary.csv](scenarios30/summary.csv): 30 строк со статусом проверки, продуктом, новой заявкой, результатом скоринга, запрошенной PD и рассчитанными условиями.
- [run_scenarios.py](scenarios30/run_scenarios.py): скрипт выполненного запуска. Учётные данные читаются из синтетической БД в памяти и не выводятся в отчёт. ID заявок и длительности при повторении будут другими.

Для повторения нужен отдельный запущенный Docker-контур выбранной версии, модель и **новая тестовая БД**. Имена ниже зафиксированы в скрипте; не направляйте его в существующую рабочую БД и не восстанавливайте дамп поверх неё. Если одноимённая тестовая БД уже есть, создайте новый изолированный контур либо явно измените тестовое имя в копии скрипта; проверка префикса `aurelius_test` должна сохраниться.

Из корня репозитория (учётка `aurelius` соответствует шаблону `.env`; при её смене подставьте свою):

```sh
docker compose exec -T db createdb -U aurelius aurelius_test_scenarios_20261026_r2
docker compose exec -T db pg_restore --exit-on-error --no-owner --no-privileges -U aurelius -d aurelius_test_scenarios_20261026_r2 /seed/business_scoring.backup
docker compose cp docs/technical/testing/scenarios30/run_scenarios.py app:/tmp/run_scenarios.py
docker compose cp docs/technical/testing/scenarios30/scenarios_30.csv app:/tmp/scenarios_30.csv
docker compose exec -T app python /tmp/run_scenarios.py
docker compose cp app:/tmp/scenarios30 ./scenarios30-repeat
```

Каждую команду выполнять после успешного завершения предыдущей. Скрипт поднимает настоящий HTTP-обработчик на свободном loopback-порту внутри контейнера и использует указанную тестовую БД. Результаты пишутся в `/tmp/scenarios30`; после завершения их нужно скопировать до удаления контейнера. Для изоляции от работающего кабинета рекомендуется отдельный Compose-проект. Повтор на более новом коде оформляется самостоятельным протоколом с новым hash.
